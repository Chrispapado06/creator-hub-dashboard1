# theicefall-shopify — Conversation Archive

## What this project is

`theicefall-shopify` is a redesign project for **theicefall**, a mountaineering/outdoor-apparel Shopify store (live storefront domain `theicefall.myshopify.com` / `theicefall.com`). The brand's actual voice is "Climb to the top" — Everest photography, alpine/summit imagery — selling a small catalog (T-shirts to start; tents referenced further down the homepage). Products are fulfilled print-on-demand through an installed app called **Tapstitch**, so the store carries no physical inventory of its own.

The entire body of work in this archive comes from a single long session on **2026-07-20** (evening, ~19:32–22:02 UTC, with one stray background-task notification the next morning). That session is the origin of the per-project memory note `project_theicefall_shopify.md` and covers everything from initial access setup through a live redesign push and a conversion-audit pass. No other transcript in the project history has substantive theicefall content — the two other files that matched a grep for "theicefall" only reference it in passing (a memory-index listing and this same archival task being set up), not in actual design/build conversation.

## Why it was built

The user asked, essentially out of nowhere, "can i give you access to my higgsfield and shopify so you design my store?" — wanting a visual redesign of the theicefall storefront, using Higgsfield (an AI image-generation tool the user already had set up from an earlier project, "Hermes") for product photography/hero imagery. There was no formal spec beyond that; direction was extracted conversationally as the session went, including explicit reference brands (Arc'teryx, The North Face, Kailas Gear) the user wanted the new design to feel like, and a later ask to also run a conversion-optimization pass ("did you optimise the sales and the funnel so we extract all from customers").

## Getting access: a long, bumpy setup phase

A large fraction of the session (roughly the first half) was just getting credentials working, not design work:

- The user first tried `claude plugin install shopify-ai-toolkit@claude-plugins-official`. This plugin **does not exist** anywhere (checked the official, community, and demo marketplaces) — it was never a real thing, and the "No marketplaces configured" error was a separate, unrelated problem (the built-in marketplace hadn't been added on this machine). Both dead ends were resolved and abandoned in favor of the real path below.
- The real path used two different Shopify credential types for two different jobs:
  - **Theme file access** via Shopify's free "Theme Access" app, which issues a `shptka_...` password usable directly with the Shopify CLI (`theme pull` / `theme dev` / `theme push`). This turned out to be far simpler than the alternative below and unblocked local theme editing immediately.
  - **Admin API access** (products, content, discounts) via a Shopify **Dev Dashboard custom app** named "Claude Theme Work." Dev Dashboard apps have no "just show me a token" UI like legacy custom apps used to — it took building a small local OAuth callback server (`oauth-exchange.js`, listening on `http://localhost:8787/callback`) to complete an authorization-code exchange. A first attempt failed with `invalid_request: redirect_uri and application url must have matching hosts` because the app's "App URL" was still the placeholder `https://example.com`; fixing that to `http://localhost:8787` resolved it.
- **Store identity confusion cost real time.** The Theme Access password that worked first pointed at `icefall-sxtd1mn1.myshopify.com` — a *different, unrelated store* under the same Shopify account — and pulling its theme ("Horizon") looked like early progress but was entirely the wrong store. The user caught this ("bro your in the wrong store"). The actual backend handle for the real store is **`nkjfh4-dt.myshopify.com`**; `theicefall.myshopify.com` is only the storefront-facing alias. This gotcha is now documented in the project's memory note so it isn't rediscovered. Once corrected, the real live theme turned out to be **"Savor,"** pulled into `savor-theme/`.
- OAuth access tokens on this Dev Dashboard app kept appearing to expire unusually fast; investigation showed most of that was Claude re-checking a token before the exchange had finished writing it (a timing bug in the checking logic, not real expiry) — but re-auth was still needed several times over the session as new scopes were added (`price_rules`, `shipping`, etc.), each requiring a fresh authorize-and-approve click from the user.
- Two protected/merchant-gated Shopify scopes were hit and could not be unlocked purely via this custom app: `write_price_rules` (discount codes) and inventory/delivery-profile writes both require a separate merchant-approval step beyond normal OAuth scope requests. Where this happened, the fix was simply doing the step by hand in the Shopify admin UI rather than fighting the API wall.
- Higgsfield: the user's original account only had 0.34 image-generation credits (well under the ~1-credit minimum per generation), so a second, better-funded Higgsfield account (Plus plan, 347.5 credits) was authenticated instead via the CLI's OAuth login (after updating a stale CLI version that had a broken OAuth client registration).

## Design decisions made

- **Direction:** the user picked "luxury/dark" as the starting aesthetic — dark backgrounds, gold/metal accents, moody-premium — informed partly by seeing the storefront directly (Bash tooling could reach the live local dev preview at `127.0.0.1:9292`; the sandboxed Browser pane was blocked from the real `.myshopify.com`/`.com` domains by content-category policy the whole session). The palette landed on near-black/charcoal base with a warm gold accent (chosen over glacier-blue-white, reasoning it ties visually to an existing sunrise-over-Everest hero photo and reads "summit" rather than "streetwear").
- **The theme's design system is centralized**: a single color palette in `config/settings_data.json` → `color_palette` (background/foreground/color1-3), referenced via `{{ settings.color_palette.X }}` across section JSON. This made global recolors cheap, but surfaced a **header-contrast bug**: the transparent header's text color setting (`text_color_transparent_home` / `_collection` in `sections/header-group.json`) is pinned to whichever palette value happens to be light, and doesn't auto-track a palette flip — it had to be manually re-pointed each time the background flipped between dark and light.
- **First redesign attempt was reverted.** After the initial dark/gold pass, the user's reaction was blunt: "i dont see any design change you only made the background dark, keep it white buw i didnt see any change." This produced a concrete lesson (captured in memory as `feedback_design_work_needs_structure.md`): a palette swap alone does not read as a "redesign" to this user. The fix that followed reverted to a white/cream background with a gold accent, and — critically — added real structural/content changes instead of just recoloring: a "Shop the Collection" heading above what had been a bare product grid, a new 3-column trust/feature strip ("Alpine-Grade Materials," "Designed for the Climb," "Worldwide Shipping"), and a full rewrite of a leftover, badly mismatched food-brand demo section ("A family tradition of bold, fresh flavor" — clearly boilerplate from the AI theme-builder that generated this theme) into on-brand "Engineered for the Summit" alpine copy.
- **Email capture popup**, requested explicitly by the user (with reference sites for inspiration): built as `sections/promo-popup.liquid` + `sections/promo-popup-group.json`, rendered site-wide via `layout/theme.liquid`. It uses Shopify's own native `{% form 'customer' %}` mechanism — no third-party app — so a real submission creates an actual Customer record with marketing consent. It fires after a several-second delay, reveals a `WELCOME10` code with a tap-to-copy button and a checkout link that pre-applies the discount, and remembers dismissal via localStorage so repeat visitors aren't renagged. Copy was later revised to match brand voice (climbing metaphor: "Take 10% Off Your First Ascent") after a background research pass on reference brands came back. One real bug was caught and fixed here: the success state wasn't setting the dismissal flag, so a subscriber who closed the tab without clicking "Continue" would have been re-prompted.
- **The `WELCOME10` discount code itself had to be created by hand** in Shopify admin (Settings → Discounts) since `write_price_rules` is a protected scope the custom app couldn't get approved for in-session.

## Product/catalog work (done live, via Admin API)

- The store had **4 separate T-shirt product listings that were really one design in 4 colors** (6 size variants each). Per the user's request ("can you add those 4 products together as 1"), these were merged into a single "Essential Cotton T-Shirt" product with Color × Size variants (24 variants total), done via a custom script (`merge-tshirts.mjs` / `merge-tshirts-2.mjs`) that copied images and rebuilt the option structure through the Admin API's product PUT endpoint (a sub-resource variant-option endpoint tried first turned out not to be valid in the API version in use). The original 3 redundant listings were archived, not deleted, so the change is reversible.
- **Categories/collections were cleaned up**: both products got a proper `product_type` ("T-Shirts") and tags, and the previously-unpublished "T-Shirts" collection was published with both products in it.
- **Tapstitch fulfillment gotcha (the most consequential bug of the session):** merging the 4 products into 1 minted brand-new Shopify variant IDs for every color except the original base (Black). Tapstitch maps its own print templates to Shopify variant IDs in its *own* backend — not via Shopify metafields, and not inspectable through the Shopify Admin API at all. The user had separately flagged this exact risk ("also make sure those t shirts because they are print on demand if one colour way is order the right one goes at there house"), and the audit confirmed it: the merged product showed 6 Synced / 18 Not Synced / Fulfillment Disabled. This was fixed by hand, one variant at a time, inside Tapstitch's own UI (Products → Edit → per-variant "+ Add product" picker) — there was no bulk/API shortcut available. **Lesson recorded in memory: any future Shopify product/variant restructuring on this store must be followed by a manual check in Tapstitch's dashboard for "Not synced" counts before trusting fulfillment.**
- A second, related bug surfaced later by a conversion-audit pass: the same 18 new variants defaulted to `inventory_quantity: 0` (vs. Black's `9999999`) since the merge script never explicitly set it, causing the storefront's structured data to report them as "Out of Stock" — a real, live bug that could plausibly suppress sales and hurt Google Shopping visibility. This one was **not fully resolved by session's end**: two attempted API fixes silently failed to persist (the first targeted the wrong — old, archived — variant IDs; the second, after finding the correct live variant IDs, still didn't take, apparently because Shopify's REST variant endpoint no longer honors direct `inventory_quantity` writes for variants created this way, and the real fix needs the protected Inventory API). The session ended with this handed to the user to fix manually in the admin UI — status unconfirmed as of the last messages in the transcript.
- **Shipping was checked and found to be fine, after an initial false alarm.** A first REST API check showed both Domestic and International shipping zones with zero configured rates, which looked like a checkout-breaking problem. It turned out the API call was only seeing Shopify's empty default "General profile" — the real one, "Tapstitch: Special Line," covers all 60 products across 30 zones with real weight-tiered rates and is managed entirely by Tapstitch itself, invisible to a plain Admin API call (delivery-profile data for apps like this is protected/gated the same way price rules and inventory writes are). Net conclusion: shipping did not need setup.

## Conversion-optimization audit

Later in the session, in response to "what other stuff can we optimise on the store to boost conversions" and later "Did you optimise the sales and the funnel," a background multi-agent research/audit ran across five lenses (product page, cart/checkout, trust/social proof, retention/lifecycle, speed/mobile), explicitly excluding anything requiring fake reviews or fake urgency/scarcity given the store's genuinely unlimited POD stock. Findings, ranked and reported honestly rather than oversold:

- **Actually shipped live during the session:** the email popup; the redesign (palette + trust strip + fixed brand-story copy); removal of fake placeholder social links in the footer (they pointed at literal `facebook.com`/`instagram.com` root domains, not real theicefall accounts) plus a native payment-icons block (Visa/Apple Pay/etc., pulled from the store's real enabled methods, no fabrication); confirmation that sticky mobile add-to-cart was already natively enabled in the theme; a "Complete Your Kit" cross-sell heading on product pages; the gold add-to-cart button (fell out of the palette redesign, no extra work needed).
- **Drafted but requiring manual user action:** Shipping/Refund/Terms policy pages — Shopify gates policy-page writes (`read_legal_policies`) as a protected scope too, so instead of another OAuth round-trip, full policy copy was written to `theicefall-shopify/policy-pages-draft.md` for the user to paste into Settings → Policies by hand. That draft explicitly flags a production-time blank to fill in from the Tapstitch dashboard and recommends legal review, especially around EU/Cyprus's mandatory 14-day withdrawal rights.
- **Identified but not started by session's end:** a size chart on the Essential Cotton T-Shirt (the Everest T-shirt has one, this one didn't — sizing doubt is called out as the #1 apparel cart-abandon reason); a reviews app (Judge.me was suggested, free tier, but needs the user's own browser session to install); zero reviews/ratings anywhere on the site.

## Operational/environment notes worth keeping

- The Bash tool in these sessions runs directly on the user's own Mac (confirmed via matching `pwd` output), not a remote sandbox — so the local Shopify theme-dev preview server at `http://127.0.0.1:9292` is real and reachable from the user's own Safari. The in-app **Browser pane**, however, is a separate tool that could not reach the real `theicefall.myshopify.com`/`.com` domains at all (blocked by a content-category policy), which is why so much of the visual verification during this session happened either through the local dev server or through raw `curl`/HTTP checks instead of the Browser pane.
- One of those `curl` verification checks accidentally became a minor scare: a spike of storefront traffic from "Council Bluffs, Iowa" looked like it might be real customer interest, but was correctly identified as very likely the assistant's own verification requests (Council Bluffs is a known Google Cloud datacenter hub, and the timing lined up exactly with the `curl` checks) — a good reminder not to read automated-tool traffic as organic signal.
- Several Shopify Admin API scopes are **merchant-approval-gated beyond normal OAuth** for custom/private apps like "Claude Theme Work": price rules (discounts), delivery profiles (shipping), inventory writes, and legal policies all hit this wall over the course of the session. The consistent workaround was doing the specific action by hand in the Shopify admin UI rather than trying to force it through the API.
- A couple of destructive-looking actions were correctly held up by safety checks requiring more explicit user confirmation mid-session (writing to live inventory data, pushing a big batch of changes after a broad "Start fixing everything. START" instruction) — in each case, getting one more explicit yes/no from the user unblocked the specific write.
