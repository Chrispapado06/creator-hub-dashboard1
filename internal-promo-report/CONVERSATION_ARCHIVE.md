# Internal Promo Weekly Report — conversation archive

## What this is

A Google Sheets reporting system for an OnlyFans management agency (UNCVRD). The manager, Aran, wants one spreadsheet he can open every Monday to decide how to allocate "internal promo" — the mix of Feed posts, Story posts, and mass DMs used to cross-promote one creator's page to another creator's fans — for the coming week. He needs it to answer: which creators got promo and how many slots, how much revenue each creator's tracking links produced, and therefore who should get more, less, or no promo next week, including catching creators who get a lot of promo but produce poor results.

The whole project lives in `internal-promo-report/` as three files: `Code.gs` (data ingestion from the OF API and the schedule tabs), `Setup.gs` (builds the sheet tabs and writes every report formula), and `README.md` (install steps and a full explanation of the join logic, config, and known limitations). It is Apps Script, not a web app, by design — the deliverable has to stay entirely inside Google Sheets.

The work was done in a single long session starting 2026-07-21, continuing into the morning of 2026-07-22, driven mostly by the user relaying a rough voice-note transcript of what his boss actually wanted, plus one clarifying request mid-project ("wait im confused, can you send me something to download... and it has to be a system where every week it's generated somewhere") that split the deliverable into two parts: a one-off file Aran could review immediately, and the recurring Apps Script system for every week after.

## Why it was built this way, and the discovery process

The brief originally described two separate Google Sheets — an "Internal Promo Sheet" and a "Revenue Tracking Sheet." Before writing anything, the investigation took an unusual number of turns because almost every assumption in the original brief turned out to be wrong:

**It's one file, not two, and it isn't a native Google Sheet.** Both links Aran shared pointed at the same spreadsheet ID (`1NfHXBDXHWix05hms4azX2uGxwTLAqo70`), just different tabs. That ID is 33 characters — native Google Sheets IDs are 44 — which meant it was actually an uploaded `.xlsx` opened in Sheets' Office-compatibility mode. Apps Script cannot bind to a file in that mode: no container-bound script, no triggers, no live formulas that survive edits. This forced a hard requirement into the design: the file has to be converted via **File → Save as Google Sheets** before any of this works, producing a new file with a new URL, and whoever maintains the promo schedules has to be told to switch to editing the new file. This is called out at the top of the README as a blocking prerequisite, not a footnote.

**There is no revenue data in the source file at all.** Not sparse — zero. The workbook contains exactly one numeric cell in the entire file (a `0`), and exactly one formula in the whole file, in a hidden tab: `=SUM(H4:H95)+SUM(M4:M95)`, a revenue total someone built and never filled in. The "Revenue Tracking Sheet" the brief described didn't exist as a data source — it was aspirational column headers. Aran's own voice note resolved the ambiguity: he said revenue should come "from the tracking links with our API," which reframed the fifth tab, `Tracking Link`, from a data feed into a **link registry** — a list of which tracking URLs to go ask the OF API about.

**The workbook actually has five tabs, not two**: Feed, Story, and MM (mass DM) promo schedules, a hidden superseded draft called `Promo Schedule`, and `Tracking Link`. The `Tracking Link` tab's own column headers are backwards — it's labeled "Promoting Creator | Promoted Creator" but column A is actually the page owner (the promoted creator), verified against real rows (Blue Bear promotes Emma, and the link is `emmasonne/c21` — Emma's handle). The build ignores those header labels entirely and derives ownership from parsing the URL handle instead.

**The join key is the OF page handle embedded in each tracking URL**, e.g. `onlyfans.com/emmasonne/c21` — the handle before the slash identifies whose page it is (who received the promo), and the `cNN` code after it identifies who sent the traffic. Revenue and slots are both attributed to the promoted creator (the page owner), so "revenue per slot" describes the same person on both sides of the ratio.

**Handle-to-creator mapping had to be an explicit table, not a heuristic**, because of one specific landmine: Sandra's OF handle is `thisisjunee`, which any name-matching guess would read as "June." That exact mistake was already live in the source data (the MM tab logs one of Sandra's promos as "June"). `Config → OF Handle Map` exists specifically to prevent that class of bug, and unmapped handles are logged and shown as `⚠ handle` rather than silently zeroing a creator's revenue.

**The OF API's `daily_metrics` field, not the summary/list totals, was the key to making the report accurate from week one.** The project's own codebase already had a hard-won warning about this (in `supabase/functions/telegram-webhook/index.ts`, and independently in `ad-tracker`'s README): the `/tracking-links` list endpoint and the `stats` endpoint's `summary.*_total` fields are **lifetime totals even when you pass `date_start`/`date_end`** — only the `daily_metrics` array actually respects the requested window. Because of this, the ad-tracker project (a related but separate project in this repo) had to build a hidden `_Snapshots` tab and do day-over-day differencing to fake weekly figures. This report avoids that entirely by summing `daily_metrics` directly, which means "Previous Week Revenue" and week-over-week change work correctly on the very first run instead of needing two weeks of history to warm up.

## Architecture and the design tradeoff at its center

The chosen split: **Apps Script only fetches and writes plain values** into two hidden-ish raw tabs (`Raw Slots`, one row per delivered promo slot, normalized out of three differently-shaped schedule tabs; and `Raw Revenue`, one row per OF page per week, pulled from the API). **Weekly Report and Summary are pure spreadsheet formulas** over those raw tabs plus a `Config` tab of named thresholds (`CFG_MinSlots`, `CFG_HighSlots`, etc., not bare cell references). The deliberate reasoning: no script ever writes a "reported" number directly, so Aran can click any cell in the report and see exactly what produced it, and nothing recalculates invisibly behind his back. The tradeoff is that the recommendation logic — a cascading IF formula six branches deep — lives in a single very long `ARRAYFORMULA` string built up in `Setup.gs`, which is powerful but hard to hand-edit; the Config tab exists precisely so nobody needs to touch that formula to retune thresholds.

The recommendation logic itself, in priority order: no slots and no revenue → "No Data"; revenue with no slots → "Increase Allocation" (earning without help); many slots and low revenue → "Reduce Allocation" (the "poor results" case Aran specifically asked for); revenue-per-slot beating the roster average by a configurable factor *and* clearing an absolute dollar floor (so a single lucky slot can't read as a breakout) → "Increase Allocation"; well under the roster average → "Reduce Allocation"; otherwise → "Keep Current." `MinSlots`/`MaxSlots` act as guard rails so no recommendation pushes a creator past an agreed range.

Also decided: only links present in the `Tracking Link` registry (and, after a later fix, links actually seen in the promo schedules) count toward revenue — this scopes the report to internal promo specifically and excludes paid-ad traffic that might hit the same pages, which is tracked by the separate `ad-tracker` project.

## Deliverable #1: the one-off file sent to the boss

Midway through the build, the user realized the Apps Script plan wouldn't produce anything Aran could look at *today*, and asked for something downloadable to send immediately, with the recurring system to follow. That produced `UNCVRD Internal Promo — Weekly Report.xlsx`, a five-tab snapshot workbook covering the week of 13–19 July 2026, built with real formulas (not hardcoded results) and checked against a completely independent recalculation before sending — a deliberate step, because it caught a real bug: the de-duplication logic was collapsing two separate mass DMs into one whenever the same promoter sent for the same creator on the same day with a different caption (Marissa had sent two distinct DMs for Julie on 15 July). That undercounted Julie by one slot and, projected across the week, four slots total; the fix was applied to both the one-off workbook and the ongoing `Code.gs` logic. The workbook shipped with revenue columns intentionally blank and highlighted, with instructions to paste in numbers once available — the honest state of the underlying source data at that point.

That snapshot also surfaced the first real findings for Aran, independent of the tooling questions: four creators (Apple, Ashleigh, Bella Leah, Meg) had zero slots and zero tracking links, sitting under a literal `To add;` note at the bottom of the registry tab; Sandra had dropped from 1 slot the prior week to 0; and Feed/Story slots were already on an almost perfectly even fixed rotation for nearly everyone, meaning essentially all of the real variance in "who gets more or less promo" was concentrated in mass DMs (ranging from 7 for Antonella/Blue Bear down to 0 for Nicole) — reframing the manager's question from "how do we allocate internal promo" to, in practice, "how do we allocate mass DMs."

## Deliverable #2: the recurring system, and the bugs a self-review caught

After the one-off file, work returned to the permanent Apps Script system. Because Apps Script can't be executed or unit-tested locally, the finished `Code.gs`/`Setup.gs` were put through an adversarial multi-lens automated review (checking the code against the real spreadsheet data across several independent "lenses") before being trusted. That review is the single most consequential part of this project's history: it surfaced at least 13 confirmed findings (and correctly refuted roughly two dozen others), including two criticals that would have made the shipped system actively harmful rather than merely incomplete:

- **The revenue link universe was built only from the `Tracking Link` registry tab**, which covered just 10 of the roster's ~14 OF handles. Four creators' handles (`marissa.munoz`, `mayyy.leee`, `bella_leaa`, `rosewhitex` — Marissa, Maylee, Bella Leah, and Nicole) never appeared in the registry at all, so no API call was ever made for their links and they would report exactly $0 revenue every single week, silently, with no log entry (the logging was itself keyed off registry entries, so anything absent from the registry produced no warning). Concretely, in the last complete week at the time, Marissa had 15 slots and Maylee had roughly 13–14, both well above the "high slots" threshold — with $0 revenue, the recommendation formula would have told the manager to *reduce* the two most heavily-promoted creators in the roster, every week, forever, for a data gap rather than a real performance signal.
- **The date field read off the API's daily-metrics rows was wrong.** The code tried `d.date || d.day || d.created_at`, but the OF API's actual field name (confirmed against the sibling `ad-tracker` project's own working code) is `timestamp`. Every daily row would have failed to parse, `Raw Revenue` would have been written with a header row and nothing else, and the recommendation cascade would have told the manager to reduce allocation for the entire roster — the same silent-zero failure mode as the registry bug, but total instead of partial.

Both were fixed: the link universe now comes from the union of the registry *and* every tracking link actually seen while normalizing the promo schedules (deduplicated by URL), and the date parse now reads `timestamp` first. A handful of smaller but real fixes came out of the same review pass and were also applied: a case-sensitivity bug in the name-canonicalization helper (`canonName_`) that could split one creator into two different-cased rows; the "week start" values being written as text in the raw tabs while the report's `SUMIFS` formulas expected real dates (or vice versa — the fix standardized on timezone-independent string date keys throughout, sidestepping an entire class of timezone bugs); and a hidden "tracked" helper column (`H5` in the report tab) meant to distinguish "this creator genuinely earned $0" from "this creator's OF account isn't wired to the API at all," so a data gap can't misread as poor performance.

## Where the work was actually left off

The session ended mid-edit, cut off by a dropped connection ("API Error: Connection closed mid-response") partway through what was described as the last remaining fix: rewriting the `G5` recommendation formula to make "Increase Allocation" reachable in every case, wire in the new "Not Tracked" state using that `H5` helper column, and guard the degenerate case where every creator has zero revenue (which would otherwise make the roster average zero and cause a divide/threshold issue in the "reduce" branch). Checking the actual `Setup.gs` on disk against that stated intent confirms the edit did **not** fully land: the `H5` tracked/not-tracked helper column exists and is computed, but the `G5` recommendation formula never references it — there is no "Not Tracked" output today, and the `MaxSlots` gate on the "Increase Allocation" branch that was flagged for removal is still present. This is a real, verifiable gap between stated intent and shipped code, not a stylistic choice — it's the one piece of unfinished business from that session.

Everything else the review flagged as critical (the two silent-zero-revenue bugs) was fixed and is reflected in the current `Code.gs`/`Setup.gs` on disk. The project has never been committed to git — `internal-promo-report/` still shows as untracked in `git status` as of this writing.

## Current status and what's left

As of today the three files on disk (`Code.gs`, `Setup.gs`, `README.md`) represent a system that has been written, self-reviewed, and mostly hardened, but **not yet installed or run against live data** — it was never confirmed whether Aran actually converted the source `.xlsx` to a native Google Sheet, pasted in the `ONLYFANSAPI_KEY`, or ran `setup()`. The README's install steps (convert the file, paste both scripts into Apps Script, add the API key to Script Properties, run `setup`, refresh, install the auto-refresh triggers) remain the next concrete steps for whoever picks this up.

Known limitations that are documented but not solved, and would need a product decision rather than a bug fix:

- **Story-tab slots can never earn revenue** — the Story schedule has no tracking-link column at all, so Story slots inflate a creator's slot count while contributing nothing to revenue, dragging down their revenue-per-slot. The workaround in `Config` (`Weight_Story = 0`) exists but changes what the ratio measures.
- **All slot-channel weights default to 1**, treating a mass DM and a Feed post as equally valuable, which they almost certainly are not — nobody had set real weights as of the last session.
- **Most schedule rows carry an `Expired` status**, currently treated as a delivered slot on the assumption that it just means the link expired after the post ran; if that assumption is wrong, flipping `ExcludedStatuses` to include `Expired` would change slot counts significantly.
- The still-open `G5`/"Not Tracked" fix described above.

Finally, and worth restating because it's easy to lose in the mechanics: the source spreadsheet itself has *no revenue history* prior to whenever the API pull is switched on — everything before that point in the Feed/Story/MM tabs is promo-slot scheduling data only, pasted or maintained by hand, with revenue always intended to come from the live API rather than from anything in that workbook.
