# daily-data-bot — conversation archive

## What this is

`daily-data-bot` is a Telegram bot for UNCVRD's VAs ("posters"). Each VA fills in a short guided checklist about their daily outreach work, and once a day everything gets rolled up into a single summary message sent to one person (originally referred to as "Aran", Telegram handle `@Freegarda`). It follows the same conventions as the other bots already in this repo (`payout-bot`, `drive-vault-bot`, etc.): zero-dependency Node `.mjs` scripts, Telegram Bot API over plain `fetch`, Supabase (PostgREST) for storage, all wired together with GitHub Actions.

The whole thing was built in essentially one sitting, starting the evening of 8 June 2026, in a single Claude Code session. The conversation is the clearest example in this repo's history of a build that went through a real live-fire deployment: a database was created, a real Telegram bot was registered, a real person messaged it, and the hosting model was changed midway through the session once the first approach proved unworkable in production.

## Why it was built

The request that kicked things off was blunt and short: "i want you to build me a bot where VAs put daily data in and that data in the end of the day gets sent to one person." Before writing anything, Claude read through the sibling bots in the repo (`ad-tracker`, `drive-vault-bot`, `payout-bot`) to match existing conventions, then used a clarifying-questions pass to pin down specifics: Telegram in, Telegram out; a guided Q&A rather than a free-text or slash-command form; and which fields to capture. The initial framing — confirmed with the user — was a **daily outreach tracker**: how many lead accounts a VA followed, commented on, and liked, plus how many posts they made on the company's own profiles.

## First build: numeric outreach tracker

The first version built was a 6-question Q&A (`profile`, `follows`, `comments`, `likes`, `posts`, `notes`) with numeric answers, backed by three new Supabase tables (`daily_outreach_entries`, `daily_outreach_sessions`, `daily_outreach_state`) and two GitHub Actions workflows — one running the collector bot in ~5.5-hour shifts, one firing the digest once daily at 22:00 UTC. All three `.mjs` files were syntax-checked and smoke-tested with pure in-process function calls (no network) before anything was wired up live, and the digest's per-VA totalling/grouping logic was verified with a hand-built fake dataset. This is the version documented in the current `README.md`.

Almost immediately after this was built, the user asked "where is the bot, where do i test it" — surfacing a real gap in understanding that shaped a good chunk of the rest of the session: the code existing on disk is not the same as a bot that VAs can message. There's a recurring, patient back-and-forth in the transcript clarifying that: Telegram is the only thing anyone (VAs, the recipient, and the bot process) ever actually talks to; the bot process itself needs to run *somewhere* with a persistent connection; and a laptop that sleeps is fine for a demo but not for production. The user also asked pointed operational questions along the way ("if its on my computer how will the vas submit their daily work", "so they message the bot, then who does the bot message for report") that Claude answered with an explicit day-in-the-life walkthrough: VAs submit silently all day (each report just saves to the database, no one gets pinged), and only once a day does a separate job gather everyone's entries into one digest to the one recipient.

## The pivot: yes/no checklist, not numeric counts

Partway through setup, the user supplied the actual questions they wanted, which turned out to be a completely different shape from what had been built:

> Have you sent the DMs? / Did you need to post today? / Have you posted stories? / Have you commented under posts? / Have you liked posts? / Are you fully completed for today?

This changed the bot from "count how many things you did" to a **yes/no daily checklist**, which Claude judged (and the user accepted) as objectively simpler for VAs to fill in on a phone — tap Yes/No buttons rather than type numbers. This is the version that shipped and is what's on disk today: `config.mjs`'s `FIELDS` array now holds `dms_sent`, `needed_post`, `posted_stories`, `commented`, `liked`, `completed`, each rendered with a Telegram reply-keyboard of `Yes`/`No` buttons (`YES_NO_KEYBOARD` in `config.mjs`), and a `parseYesNo` fallback so a VA who types "yes"/"nope"/"✅"/etc. instead of tapping still works. The Supabase migration (`supabase/migrations/20260609120000_daily_outreach.sql`) was edited in place to boolean columns matching the new fields, and the user was walked through re-running the changed SQL directly in the Supabase dashboard (drop + recreate `daily_outreach_entries`) since the Supabase CLI wasn't installed locally at the time.

The digest format changed to match: each VA's per-question ✅/❌ checklist, a `⚠️` flag next to anyone not fully completed, and a `🏁 Fully completed: X/Y` footer — this is implemented in `digest.mjs` roughly as shown, and was confirmed against a live test send.

## Getting a real bot live and testing end-to-end

The user created the actual Telegram bot via BotFather themselves (only they could — it needs their Telegram account) and it was registered as **`@ncvrd_outreach_bot`** ("UNCVRD Daily Outreach"). Claude verified the bot token worked with a `getMe` call, confirmed `.env` was gitignored before touching any secrets, and pulled the Supabase project URL from the repo root `.env`.

One small back-and-forth worth noting for posterity: the user initially pasted a Supabase **publishable** key rather than the `service_role` key the bot's config technically asks for. Rather than blocking on it, Claude tested the key directly against the REST API (a GET and a write against `daily_outreach_state`) and confirmed it worked fine for this table — because the RLS policies on these tables are deliberately permissive (`FOR ALL TO anon, authenticated USING (true) WITH CHECK (true)`, matching the `ad_tracker` migration's style, since this is treated as a single-user internal tool). So the bot ran on the publishable key rather than blocking on getting the true service-role secret — a pragmatic call flagged as swappable later if tighter security is ever wanted.

With the token and key in place, the bot ran locally (`node --env-file=.env bot.mjs`) as a background process for live testing. The user tested `/report` themselves (as `@chrisofmcy`), and separately the recipient (`@Freegarda` / "Aran") was walked through connecting: since Telegram bots can only message a chat id once that person has messaged the bot first, Aran had to open the bot and send anything (he sent "Hi"), at which point Claude read his chat id out of the bot's own log (`1399654185`) and set it as `TELEGRAM_RECIPIENT_CHAT_ID`. A real end-to-end test digest was then sent for the test entry logged the day before, and the user/Aran confirmed receipt — proving the full loop worked: VA fills checklist → saved to Supabase → recipient gets a summary.

## Hosting: GitHub Actions, then a pivot to a Vercel webhook

The code (bot, config, digest, README, `.gitignore`, the migration, and both workflow files) was committed and pushed to `main` on the connected GitHub repo (`Chrispapado06/creator-hub-dashboard1`), after a dry-run confirmed exactly the intended 9 files would be added and no secrets would leak. GitHub secrets were added for the new bot — but note the repo already had a `TELEGRAM_BOT_TOKEN` secret in use by other bots (payout-bot, drive-vault-bot); adding a same-named secret would have silently pointed those other bots at the wrong token. Claude caught this before damage was done and renamed everything to an `OUTREACH_`-prefixed set (`OUTREACH_BOT_TOKEN`, `OUTREACH_SUPABASE_URL`, `OUTREACH_SUPABASE_KEY`, `OUTREACH_RECIPIENT_CHAT_ID`) so the new bot's secrets can never collide with any other bot in the repo. This prefix convention is what's actually in use today.

A few days later (11 June), the user reported the collector wasn't working ("Aran said /report doesnt work"). Diagnosis: Telegram's `getUpdates` showed several `/report` messages sitting completely unprocessed — nothing was listening. The root cause was architectural: **GitHub Actions is a bad fit for a long-polling Telegram bot.** The scheduled/shift-based collector workflow only runs when a job is actively triggered or its cron fires; it doesn't hold an always-on connection the way `bot.mjs`'s long-poll loop needs. Claude was explicit that this would keep happening as long as the live-reply half of the bot depended on Actions.

The fix was to move the "collector" half to a Telegram **webhook** hosted on Vercel, since the repo was already a Vercel-deployed Vite app. Concretely:
- A new self-contained serverless function, `api/outreach-bot.js`, was written — it duplicates the checklist logic from `daily-data-bot/config.mjs`/`bot.mjs` on purpose (no cross-directory imports, so Vercel's bundler can't break it) and reads its own `OUTREACH_`-prefixed env vars plus a webhook shared secret (`OUTREACH_WEBHOOK_SECRET`, generated via `openssl rand -hex 24`) used to verify incoming requests are really from Telegram.
- `vercel.json`'s SPA catch-all rewrite (`"/(.*)" → "/index.html"`) had to be adjusted so it didn't swallow requests to `/api/outreach-bot`.
- The old GitHub Actions **collector** workflow (`daily-data-bot.yml`) was deleted — a webhook and a polling collector can't run simultaneously against the same Telegram bot (Telegram only allows one `getUpdates` consumer, and a webhook replaces polling entirely).
- The **digest** workflow (`daily-data-digest.yml`) was kept on GitHub Actions, since a once-a-day cron job is exactly what Actions is good at — it was only updated to use the same `OUTREACH_`-prefixed secrets.
- After confirming the Vercel deployment's env vars were actually loaded (a `GET` health-check endpoint on the function reporting `{"up":true,"env":{"token":true,"supabase":true,"secret":true}}`, since Vercel only bakes in env vars added *after* a deploy on the next build), Claude called Telegram's `setWebhook` pointing at `https://creator-hub-dashboard1.vercel.app/api/outreach-bot` with the shared secret, confirmed via `getWebhookInfo` that Telegram had it set with zero pending updates, and stopped the local Mac process for good.

The transcript ends here — the last messages are Claude confirming the webhook is live and healthy, distinguishing a genuinely benign old failed-build screenshot (a transient `ECONNRESET` on an earlier commit, superseded by a working deploy) from a real problem, and asking the user to send one more live `/report` to `@ncvrd_outreach_bot` as final confirmation. There is no further transcript content after that showing the final confirmation reply.

- **`daily-data-bot/bot.mjs` and its README are stale relative to that outcome.** `bot.mjs` still contains the original long-poll collector logic and is not what's actually answering VAs in production anymore — that's now `api/outreach-bot.js` on Vercel. `bot.mjs` is presumably kept around as the source of truth for local testing/dev, and its logic is deliberately mirrored (not shared) in the Vercel function.
- **`daily-data-bot/README.md` is significantly out of date.** It documents the *first* version of the bot — the numeric outreach tracker (profile/follows/comments/likes/posts/notes) — not the yes/no checklist that actually shipped (`dms_sent`, `needed_post`, `posted_stories`, `commented`, `liked`, `completed`, all boolean). It also still describes the GitHub Actions shift-based collector as the way to run the bot 24/7, with no mention of the Vercel webhook that replaced it in production. Anyone picking this project back up should treat the README as describing the *pre-pivot* design, not the live system, and should update it (or point to `api/outreach-bot.js`'s own header comment, which is accurate) before relying on it.
- **`daily-data-bot/.env` locally holds** `TELEGRAM_BOT_TOKEN`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `TELEGRAM_RECIPIENT_CHAT_ID` — the non-prefixed names used for local testing of `bot.mjs`/`digest.mjs`, distinct from the `OUTREACH_`-prefixed secrets actually used by the deployed Vercel function and the GitHub Actions digest workflow.
- The digest cron (`daily-data-digest.yml`) fires at `3 22 * * *` (22:03 UTC) and still uses `OUTREACH_`-prefixed secrets pulled from GitHub Actions secrets, matching the final state reached in the session.
