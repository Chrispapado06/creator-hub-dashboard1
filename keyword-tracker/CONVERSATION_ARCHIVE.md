# keyword-tracker — project history

## Read this first: the folder name is misleading

`keyword-tracker/` is a real, working Next.js app that still lives on disk and still runs (`PREVIEW_MODE=1` is set in its `.env.local`, so opening it today shows mock/sample data, not live data). But it is **not** the thing anyone actually uses day-to-day. Its own README describes a "keyword attribution ROI dashboard," which was the original idea — but that idea was explicitly abandoned partway through the project's life, and the app was rebuilt in place into something else (an experiment tracker), which was *itself* then ported out of this folder into the main `creator-hub-dashboard-main` app, where it lives today as the "OnlyFinder" sidebar platform. What's left in `keyword-tracker/` is effectively a fossil containing two superseded generations of the idea. Nothing in this folder is in git (`git status` has always shown it as `??`), and nothing here has been touched since June 20.

The rest of this document is the actual story, reconstructed from session transcripts, in chronological order.

## Act 1 — the original keyword-attribution ROI dashboard (June 5, 2026)

The project began from a pasted spec: "Build a keyword attribution tracking dashboard for OnlyFans creators running ads on OnlyFinder" — map OnlyFinder ad keywords → OnlyFans tracking links → subscribers → revenue, so the user could see ROI per keyword and know what to scale or cut. The spec asked for Next.js 14 + Supabase + Tailwind, with four tables (`creators`, `tracking_links`, `keyword_costs`, `subscriber_snapshots`) and four pages (`/dashboard`, `/links`, `/costs`, `/sync`).

The first real decision came immediately: the pasted spec assumed a fresh Next.js project, but the main repo (`creator-hub-dashboard-main`) is actually a mature TanStack Router + Vite + React 19 app with its own Supabase setup and an existing `creators` table and OnlyFans API client. Rather than duplicate `creators`, the build was scoped as a **standalone Next.js 14 sub-app** in `keyword-tracker/`, pointed at the *same* Supabase project, reusing the existing `creators` table, and adding only three new tables via a migration in the parent repo's `supabase/migrations/` (`20260606120000_keyword_attribution.sql` — this file still exists and has never been applied). This "standalone Next.js app in a subfolder of the main repo, same Supabase project" pattern became a convention the user reused for later sub-apps (see Act 2).

A second deliberate deviation from the spec: the OnlyFans API client was written to use `Authorization: Bearer <key>`, not the `x-api-key` header the spec mentioned, because that's what the production dashboard's real `of-api.ts` actually uses against `app.onlyfansapi.com`. This is called out explicitly in the README.

The build itself went smoothly except for two environment gotchas worth remembering if this ever gets touched again:
- The global npm cache (`~/.npm/_cacache`) had root-owned entries that blocked `npm install`; it was worked around with a temporary project-local cache (the fix suggested at the time, never confirmed done: `sudo chown -R $(whoami) ~/.npm`).
- `tsconfig.json` needed an explicit `target` — Next.js injects one at build time but bare `tsc` does not, and stale `tsconfig.tsbuildinfo` pinned the wrong target until cleared.

Because the real Supabase migration hadn't been applied yet and there was no service-role key configured locally, the assistant added a `PREVIEW_MODE` flag (isolated entirely in `src/lib/mock.ts`) so the four pages could be shown with realistic sample data via headless-Chrome screenshots, without touching the real database. That flag is still set to `1` in `.env.local` today — meaning it was likely never switched over to live data before the project moved on to Act 3.

## Act 2 — keyword-tracker becomes "the pattern" for other tools (June 6–13)

The day after, a related but separate project (`ad-tracker/`, the "UNCVRD Ad Tracker" — a Google Sheets + Apps Script system for Meta + OnlyFinder ad spend) was built as a sibling folder, explicitly modeled on how `keyword-tracker/` was structured. While grounding that build, the assistant discovered and reported an important fact that also matters for `keyword-tracker` itself: **neither OnlyFinder nor OnlyGuider has a public API** — both are scraper-based directories, so keyword-level spend/click data can only ever be typed in by hand; only the OnlyFans-side subscriber/revenue numbers can be pulled automatically. This is exactly why `keyword-tracker`'s `/costs` page was designed as manual data entry rather than an integration.

A week later (June 13), when building a third standalone sub-app (`viability-scorer/`, a Reddit-viability scorer for creators), the assistant again explicitly followed "the precedent of `keyword-tracker/`, which is already a Next.js sub-app in this repo" — reading its `package.json` and conventions before scaffolding. That session is also where a recurring gotcha was written down as a permanent lesson (now in project memory as `feedback_no_build_during_dev.md`): **never run `npm run build` while `npm run dev` is running** in these Next.js sub-apps — both write to the same `.next` directory, and a production build clobbers the dev server's compiled CSS, making the app render as unstyled black-on-white HTML. It bit the user twice on `viability-scorer`; the same risk applies to `keyword-tracker`.

## Act 3 — the pivot: "this is an experiment tracker, NOT a per-keyword attribution system" (June 15)

On June 15 the user came back with a new brief — `onlyfinder-experiment-tracker-brief.md` — and opened with four hard rules that directly repudiate Act 1's whole premise:
- This is an **experiment tracker**, not a per-keyword attribution system. Never generate logic that claims to attribute a specific fan to a specific keyword.
- Do not build any OnlyFinder dashboard scraper.
- OnlyFans data comes from the OnlyFansAPI REST API with a server-side key, never a Claude MCP connector.
- One keyword change at a time per creator; a confounded observation window must never produce a verdict.

In other words: after living with the original ROI-per-keyword model for a week and a half, the user concluded it was the wrong model — you can't cleanly attribute revenue to a keyword — and asked for something more honest: log one keyword change per creator, watch a fixed before/after window, and only issue a Scale/Hold/Kill verdict when the window wasn't muddied by other changes.

Getting this off the ground took two attempts because of a file mix-up: the user pointed at `onlyfinder-experiment-tracker-brief.md` as "the full spec," but it was actually an **empty directory** (a leftover Claude Code session folder, not a markdown file) — so no spec content existed anywhere on disk. This blocked a first session entirely (it stalled after asking the user to paste the brief or pick a folder to scaffold into, and got no reply). A second attempt, minutes later in the main repo's context, hit the identical wall. Rather than fabricate a schema and silently diverge from an unknown "Section 4," the assistant refused to guess, and the user then explicitly authorized the assistant to **design the schema itself from the four stated rules** (flagged as an assistant design, to be reconciled against the real brief later if it ever turned up — it never did). The user also picked, when asked to choose between two ways of handling fan counts from platforms other than OnlyFinder: **Option A** — other platforms' fans/income are tracked separately, with a mandatory, auditable subtraction (`direct_fans = total_new_fans − tracked_fans`), rather than leaving `total_new_fans` contaminated.

Before writing any new scaffolding, the assistant found that `keyword-tracker/` already had exactly the stack the brief wanted (Next.js 14 App Router, Tailwind, a working Supabase server client, a working OnlyFansAPI client) and that its own README's language ("OnlyFinder," "ROI," "confounded") was clearly the ancestor of this brief. So rather than create a fourth project, **the experiment tracker was built directly into `keyword-tracker/`, superseding the old attribution pages** (`/dashboard`, `/links`, `/costs`, `/sync` — still present as files, but unlinked from navigation from this point on).

The build proceeded stage by stage:
- **Database** — `keyword_changes` (the intervention log), `daily_metrics` (per-creator/day totals plus the Option-A tracked/direct split), `daily_tracked_sources` (per-platform audit trail), `keyword_rankings`, and `experiments` (a `running` / `confounded` / `concluded` / `insufficient_data` state machine). A Postgres trigger auto-creates the `experiments` row the moment a `keyword_changes` row is inserted, and a `CHECK` constraint makes it structurally impossible for a `confounded` row to also hold metrics — the "confounded windows never get a verdict" rule is enforced by the database, not just app code.
- **Experiment engine** (`experiment-engine.ts`) — a dependency-free pure module (so it can run identically in a Deno Edge Function and in Vitest): baseline window = change_date−7..−1, observation window = change_date+1..+7, confound = any *other* keyword change landing inside `[baseline_start, observation_end]`, and lift computed on fans-per-day, income-per-day, and fans-per-dollar-of-spend (so windows with different ad spend stay comparable). Shipped with 9 passing unit tests.
- **Daily digest** (`digest.ts`) — calls the Anthropic Messages API (model `claude-haiku-4-5`) with each creator's running/just-concluded experiments, forces structured JSON output via tool-use, and returns a one-line status, an early/final read, a recommended action, and any confound warning per experiment, plus a prose summary. The three hard rules are placed in the system prompt **and** re-enforced in a `sanitizeDigest()` post-processor, on the reasoning that a prompt can be ignored by the model but a code guardrail can't — verified by a test that feeds in a model response trying to recommend "scale" on a confounded experiment and asserts the code forces it back to "unreadable."
- **UI** — four pages built into `keyword-tracker/`: `/` (Creators list + Add-Creator form), `/creators/[id]` (a hand-rolled SVG fans/income chart with markers at each keyword change, an experiments table, and quick-entry forms for spend and keyword changes), `/decisions` (Scale/Hold/Kill columns from concluded experiments), `/digest` (the stored Claude readout). This is the origin of the `tracker-db.ts` / `tracker-types.ts` / `tracker-actions.ts` files and the `components/tracker/` folder still sitting in this repo today.

## Act 4 — the scope correction: it was supposed to live in the main dashboard (June 15, later that day)

When the user asked why the new work wasn't visible at `creator-hub-dashboard1.vercel.app/ads`, the answer was that the brief's own wording ("standalone Next.js app") had pulled the build away from what the user actually wanted from the start — a section *inside* the existing dashboard's `/ads` page. The assistant flagged this as its own mistake for not catching the contradiction earlier.

The fix: **port the whole thing into the main Vite + TanStack Router dashboard**, reusing every framework-agnostic piece (the Postgres schema, the experiment engine, the digest module) and rebuilding only the UI in React/shadcn/recharts. This is why `keyword-tracker/`'s experiment-tracker UI and the current, real "OnlyFinder" feature look so similar but live in two different codebases now. The ported version was wired into `/ads` as a new "OnlyFinder" tab, then — per a follow-up request the same day — promoted to a first-class sidebar entry under "Platforms" (alongside OnlyFans, Reddit, X, TikTok, Meta) with its own logo (a pink magnifier+heart mark the assistant designed, since it couldn't fetch OnlyFinder's real brand asset). Getting the sidebar link to actually appear required also registering `onlyfinder` in the app's page-access allowlist (`admin-pages.ts`) — without that, the link would have stayed invisible even to the super-admin account, since that allowlist gates visibility regardless of role.

This work is genuinely live and in git, unlike anything in `keyword-tracker/`:
- `3ae6409` — "ads: add OnlyFinder experiment tracker section (/ads → OnlyFinder tab)"
- `635a5ce` — "nav: add OnlyFinder as a Platforms sidebar entry with its logo"
- `f7582f5` — "onlyfinder: modern DatePicker for keyword-change + spend forms" (a same-day UI polish pass, swapping the native date input for the app's existing popover `DatePicker` component)

The five Supabase migrations that back this feature also live in the main repo's `supabase/migrations/`, separately from `keyword-tracker`'s own never-applied migration: `20260615120000_onlyfinder_experiment_tracker.sql`, `20260615140000_experiment_engine.sql`, `20260615150000_daily_digest.sql`, `20260615160000_creator_tracker_fields.sql`, `20260615170000_tracked_cumulative.sql`.

## The adversarial review — and the gap that was never closed

Later the same day, the user asked for a genuinely adversarial self-review against an 11-point checklist (off-by-one errors in the window math, whether a spend change mid-window also counts as a confounder, negative-value clamping, idempotency, timezone consistency, a noise floor for small sample sizes, and — most importantly — whether the "code-enforced guardrail" on verdicts was real code or just prompt wording). Six reviewer passes ran in parallel and returned 48 findings, most of them "correct and tested" (the window math, the confound-boundary inclusivity, the digest guardrail all checked out with real unit tests pointed to).

But the headline finding subsumed half the checklist: **the orchestration function was never written.** `supabase/functions/daily-pull/` contains only `experiment-engine.ts`, `digest.ts`, and their test files — there has never been an `index.ts`, and nothing in the codebase calls `evaluateExperiment` or `generateDailyDigest`. The engine and the digest module are well-unit-tested in isolation, but nothing bridges them to the OnlyFansAPI, to a daily cron, or to the database in production. No Supabase cron schedule was ever added, either. This is still true as of this reconstruction — `supabase/functions/daily-pull/` has exactly the same four files, last modified June 16, and no commit has ever touched it beyond the initial one.

The practical consequence, visible in the current code (`src/lib/onlyfinder.ts` in the main dashboard): the only field a user can actually write into `daily_metrics` today is `onlyfinder_spend_usd` (there's a manual "log daily spend" form). There is no manual or automated path that ever populates `total_new_fans` / total income / the tracked-per-platform numbers the experiment engine needs — those were only ever meant to arrive via the missing daily-pull cron. So in production today, keyword-change experiments can be logged and will auto-create a `running` row, but they almost certainly never accumulate real fan/income data, never reach a `concluded` state, and the `/digest` view has no digest to show. The Decisions page, Scale/Hold/Kill logic, and the lift-percentage math are all real and tested, but effectively idle without that missing piece.

Right after the review, the conversation moved on to an unrelated topic (a Twilio/WhatsApp task-notification bug) and never returned to close this gap — Stage 6 of the original plan ("make it run unattended": deploy the Edge Function, schedule the cron, walk through every Vercel/Supabase env var) was requested by the user but never delivered.

## Current status, summarized

- **The live, real feature** is the "OnlyFinder" platform in the main `creator-hub-dashboard-main` app (sidebar → Platforms → OnlyFinder, route `src/routes/onlyfinder.tsx`, UI in `src/components/onlyfinder/`, data layer in `src/lib/onlyfinder.ts`). It is committed to `main` and deployed to `creator-hub-dashboard1.vercel.app`.
- **This folder, `keyword-tracker/`**, is not that. It is an untracked, never-committed standalone Next.js app that went through two full generations of design (the original per-keyword ROI dashboard, then — built in place over the top of it — the experiment-tracker UI that was subsequently re-implemented in the main app). Both generations of pages/files are still physically present here (`dashboard/`, `links/`, `costs/`, `sync/` from generation one; `page.tsx` (Creators), `decisions/`, `digest/`, `creators/[id]/`, and the `tracker-*` lib files from generation two), but neither is what anyone actually uses.
- **`PREVIEW_MODE=1`** is still set in this folder's `.env.local`, so if it's ever run again (`npm run dev`), it will render mock/sample data, not real Supabase data.
- **The one substantive open bug that matters going forward** lives in the main app, not here: `supabase/functions/daily-pull/index.ts` needs to be written (call the OFAPI, upsert `daily_metrics`/`daily_tracked_sources` with the cumulative→delta diff and the direct-fans clamp, call `evaluateExperiment` per open experiment excluding the experiment's own change by id, then call `generateDailyDigest` and upsert `daily_digests`), and a Supabase cron schedule needs to be added to run it daily. Until that exists, the OnlyFinder experiment tracker has no data pipeline behind its UI.

## What's likely safe to do with this folder

Given the above, `keyword-tracker/` is a reasonable candidate to either delete outright or keep purely as historical reference — its migration (`supabase/migrations/20260606120000_keyword_attribution.sql`) has never been applied to the database, so removing the folder would not touch anything live. If any code from generation two (the experiment-tracker UI, `tracker-db.ts`, etc.) is ever needed for reference, it's fully superseded by the equivalent files under `src/components/onlyfinder/` and `src/lib/onlyfinder.ts` in the main repo, which are the ones actually running in production.
