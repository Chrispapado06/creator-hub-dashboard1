# UNCVRD Ad Tracker — Project Archive

## What this is

The UNCVRD Ad Tracker joins **ad spend** (Meta, OnlyFinder, OnlyGuider, OnlySeeker, and later OnlyTraffic) to **OnlyFans backend results** (new fans + revenue) through one join key: a unique OnlyFans tracking link per ad/split-test variant, named identically on both sides. From that join it derives CPC, CAC, click→sub conversion rate, LTV, ROAS, profit, and a SCALE / KEEP / CUT verdict per variant and per creator — the core question being whether a given ad or keyword is worth scaling, leaving alone, or killing.

The user is a non-technical operator at UNCVRD, an OnlyFans agency, building this on behalf of their manager/boss ("Aran"), who does the actual media buying and set the real requirements (see below). Almost everything in this project was driven by Aran's feedback relayed secondhand through the user, which is why the build went through so many shapes — the user was often translating what the boss said he wanted, or what he'd just tried and found broken, rather than speccing it themselves.

## How it started

The project began from a PDF the user dropped in (`UNCVRD_Ad_Tracker - README.pdf`) describing a Google Sheet + Apps Script tracker with an OnlyFans auto-pull script. Before building, Claude checked the repo and found a same-day sibling project, `keyword-tracker/` (a Next.js app), and asked the user to choose a form factor. The user picked **Apps Script + Google Sheet**, with a Supabase mirror for the data. That first pass produced the `.gs` files still in this folder — `Config.gs`, `Setup.gs` (the `buildTracker()` scaffolder), `OnlyFans.gs`, `Meta.gs`, `OnlyFinder.gs`, `Triggers.gs`, `Supabase.gs` — plus `supabase/migrations/20260606130000_ad_tracker.sql`, which defines `ad_settings`, `ad_creator_salaries`, `ad_daily_log`, and a `ad_daily_log_metrics` view replicating the sheet's formulas in SQL.

That initial build was carefully done: array-formula division was wrapped in `IFERROR` to stop `#DIV/0!` leaking into empty rows, the `.gs` files were syntax-checked with `node --check`, and global-scope constants were checked for collisions across files (Apps Script shares one global scope across all script files in a project). Practically none of this Apps Script layer ended up being the thing actually used long-term, though — see "What actually shipped" below.

## From a script to a shareable product

Almost immediately after the first build, the user asked for "a spreadsheet and a dashboard" with room for creative ideas, and separately worried about being non-technical — "im not technical so help me now, if i want to show him what do i do." That framing shaped everything after it: every deliverable had to be understandable and operable by someone who wouldn't read code. This produced `UNCVRD_Ad_Tracker.xlsx` (a real Excel/Sheets file, five tabs, sample split-test rows, verified to recalculate without formula errors) and `dashboard.html`, a self-contained, double-click-to-open visual dashboard with KPI cards, a "what to scale & cut" call list, a profit-vs-salary chart, a variant leaderboard, and a platform summary. `FOR_YOUR_FRIEND.md` was written at the same time so the user had something plain-English to forward.

### Bernard and the Data Analyst

The user then asked for an AI "marketing expert" built in, named **Bernard**, and pasted a raw `curl` example against the Anthropic Messages API to specify it. Bernard was implemented as a browser-only chat panel inside `dashboard.html` that calls the Claude API directly via `fetch` with the `anthropic-dangerous-direct-browser-access` header — the user's API key is entered once and kept in that browser's `localStorage`, never written into the shared file.

Shortly after, the user tried to add a second agent — a Claude **Managed Agent** ("Data analyst," created via the `anthropic.beta.agents` Python SDK) — pasting its creation code without initially realizing it's an entirely different architecture from Bernard: a sandboxed, Anthropic-run agent loop that executes real Python (pandas/matplotlib) and can't run from a static HTML file. This caused a long stretch of confusion — "why is it that i only see data analyst, but not the rest," "can we launch it on my terminal," "no like, can i see the software now" — because the user wanted one thing and kept getting handed separate pieces (a terminal agent vs. a browser file). The fix was a proper local app: a Python server (`data-analyst/app.py`, launched via a double-clickable `Launch Data Analyst.command`) that unified everything behind `localhost:4000` as one app with tabbed pages — **Overview**, **Creators**, **Data Analyst**, **Settings** — with the dashboard and Bernard embedded in the Overview tab. A recurring cause of "why do I still see the old version" during this period turned out to be a stale server instance still holding the port, blocking the new one from taking over.

Once unified, the app went through a round of visual polish entirely driven by the user's specific taste: light/dark theme toggle, buttons that grow slightly and flip to white-on-black on hover, and — after several rounds of "no not like that" — a thin rainbow-colored outline that traces a button's edge and rotates on hover (not a color-flipping fill, not a blurred glow: a moving line). The two stacked headers (dashboard's own header plus the app shell's) were later merged into one unified header bar once the user pointed out the duplication.

The Creators page was added so the boss could add creators, pick which ad platforms apply to each (OnlyFinder, Meta, or both), and edit salary/percentage — explicitly *not* auto-adding every creator, because the user was clear the boss wanted to choose who ads actually run for. A "read keywords from a screenshot" feature was added for OnlyFinder/OnlyGuider (platforms with no API): the boss screenshots his keyword report and Claude's vision reads out each keyword's working/not-working status plus clicks and spend, rather than the boss typing it all in — this reused the same Claude wiring as Bernard/Data Analyst. It was initially buried inside each creator's card and invisible until a creator existed, so it was promoted to a big, obvious card at the top of the Creators page.

### The deployment saga

Once the app worked locally, the user asked to deploy it "on Vercel" to share with the boss. Claude explained why Vercel doesn't fit: this is a long-running Python server with a background sync job and local-file storage for keys, and Vercel's serverless functions are stateless and short-lived. Two options were laid out — **Option A**, a read-only static snapshot (no login, no keys, Overview + Creators only) deployable to Vercel immediately, and **Option B**, the real hosted app with password login and server-side keys. The user picked A first, then asked to also set up B once the boss sent real requirements ("Main data points: ~$0.70 CPC target, ≥25% conversion rate target, and a new split test whenever conversion falls under 25%" — this became the spec for a daily report format).

Option B's hosting path itself moved twice. It first went to **Render** (free tier, no card needed, auto-deploys from a GitHub repo) with a password gate (value not reproduced here — see the `project_railway_deployment.md` memory note or Railway's environment variables) protecting the whole app. Early on the boss couldn't log in from his phone because the browser's native two-box username+password popup confused him — this was replaced with a proper single-field password page. Meta ad spend was then wired in as **per-creator** attribution rather than per-link, because the boss names Meta campaigns by creator (e.g. "sandra"), not by variant. Render's free tier turned out to sleep after ~15 minutes idle, so IMPORTDATA calls into the eventual Google Sheet would time out and — because they were wrapped in `IFERROR(...,"")` — fail silently as blank cells rather than visible errors, which is why "why is it not showing," "clicked refresh a million times," and "cant find the api on render" kept recurring. A `/warm` endpoint and a GitHub Actions keep-alive pinger were added as a stopgap, but the user (rightly) got tired of band-aiding a recurring problem, so on **2026-06-24** the server was migrated to **Railway**'s Hobby plan (~$5/mo, always-on, no cold starts) — this is documented in the existing project memory `project_railway_deployment.md` and is still the live setup as of the last activity in this project.

## The pivot back to spreadsheets

In parallel with the hosted-app work, the boss kept asking for things in spreadsheet terms — he sent his own example Google Sheet and asked "can you make a sheet that is same like that but specifically for what we want." This triggered a second track that eventually became the dominant deliverable: rather than re-adding Apps Script triggers, Claude built a **live Python server backing a Google Sheet via `IMPORTDATA`/gviz formulas** — the sheet holds zero scripts and zero triggers; every open just re-pulls fresh JSON/CSV from the same Railway server that powers the web dashboard. This removed an entire class of bugs at once (Apps Script triggers not firing, stale cached values, per-user script permissions) at the cost of the sheet being read-only for computed data and dependent on the server staying up.

This track went through several named generations, all in this folder: `UNCVRD_Ad_Scorecard.xlsx` → `UNCVRD_Ad_Scorecard_LIVE.xlsx` (first server-backed version — "no script, no triggers, no timezones, nothing to maintain") → `UNCVRD_Ad_Suite.xlsx` (a "master sheet, everything in one place" build that a dedicated adversarial-review pass checked for date-matching and formula bugs before the boss imported it) → `UNCVRD_Weekly.xlsx` (the current version, laid out to match a screenshot the boss sent of how he wanted the week to read: dates down the side, platforms and metrics across, a day-by-day breakdown, a Weekly History tab that accumulates past weeks, a Time-to-Profit / cohort view, and a Manual Spend tab for the platforms with no API). `build_master.py`, `build_scorecard.py`, `build_scorecard_live.py`, and `build_weekly.py` are the generator scripts behind each of these, in that order.

## Bugs and gotchas actually hit

A recurring, hard-won lesson was **timezone handling**. The original Apps Script trigger kept writing "today's" data into the previous day's row because Google's server clock (not the sheet's or the user's) decided what "today" was — and separately, sheets created from an uploaded `.xlsx` have no timezone set at all, so a naive fallback silently broke again. This was patched twice (first trusting the sheet's own timezone, then hard-anchoring to the user's Athens time when the sheet's setting was invalid) before it was made moot entirely by dropping Apps Script triggers in favor of the always-fresh server pull. Later, the user separately asked whether OF data could be shown in UTC+1 or UTC 0; investigation confirmed the OnlyFans API always buckets days at UTC midnight regardless of any `tz` parameter passed (the parameter is silently ignored), and that this already matches OnlyFinder's own day boundary — so there was nothing to change.

A second recurring issue was **tracking-link name matching**. OnlyFans auto-generates junk links like `Traffic/<id>/#nnn/...` that must not be confused with the boss's real "OnlyTraffic" platform links, and one creator's real link was literally named `TT Traffic` (TikTok traffic, a different channel entirely) — close enough in spelling to have been miscounted as OnlyTraffic if matched loosely. The eventual rule required both "only" and "traffic" in the name.

A third: on **2026-06-18**, the user's mentor manually overwrote click numbers directly in the live "Weekly Stats" tab for the week of Jun 12–18 (fans/revenue were left on their live formulas — only clicks were hand-edited). Before touching that sheet again, those exact numbers were snapshotted so the user could restore them after a rebuild; the full values are preserved in `ad-tracker/snapshots/snap_Weekly_Stats.csv`, `snap_Data.csv`, and `CLICKS_RESTORE_2026-06-12.txt`, and summarized in the project memory `project_mentor_click_snapshot.md`. The same discipline was applied every time a new creator was added later (Ella, then Rose White) — snapshot first, confirm nothing manually entered would be lost, then rebuild.

A fourth, smaller bug: `build_weekly.py` had its "current week" hard-coded at generation time, so the sheet quietly went stale and kept opening on a week from days earlier ("its the wrong week"). It was fixed to compute the default week from the real system date, defaulting specifically to the *last fully-completed* week rather than the in-progress one (since a Friday build of "this week" would show mostly empty days).

## What actually shipped, and what's likely stale

As of the last activity in this project (2026-07-03), the live setup is:
- A Python server (`app.py`) hosted on **Railway** (`ad-suite-production.up.railway.app`), always-on, serving live OnlyFans + Meta data as JSON/CSV feeds. The deployable copy of this server lives in a **separate** local git repo/clone at `~/uncvrd-ad-suite` (GitHub `Chrispapado06/uncvrd-ad-suite`), not inside this `creator-hub-dashboard-main` repo — the copy in `ad-tracker/data-analyst/app.py` here is the working/source copy that gets manually copied over and pushed to that other repo whenever it changes. Anyone continuing this work should be aware those two copies can drift.
- `UNCVRD_Weekly.xlsx` (v15 as of Jul 3) is the sheet the boss actually uses, pulling live via `IMPORTDATA` from the Railway server, defaulting to the last completed week, with Meta/OnlyFinder/OnlyGuider/OnlySeeker/OnlyTraffic all represented, manual-spend entry for the platforms without an API, and a Weekly History tab that accumulates past weeks without overwriting them.
- The full-featured hosted **web app** (Overview/Creators/Data Analyst/Settings, Bernard, password login) was also deployed and working at points in this project's life, but the later conversation's center of gravity moved to the spreadsheet track since that's what the boss kept asking for directly. It's unclear from the transcripts whether the hosted web app is still the thing anyone opens day-to-day, or whether the Weekly sheet fully replaced it in practice — worth confirming before assuming either is "the" current tool.
- The original **Apps Script** files (`Config.gs`, `Setup.gs`, `OnlyFans.gs`, `Meta.gs`, `OnlyFinder.gs`, `Triggers.gs`, `Supabase.gs`) and the **Supabase migration** (`20260606130000_ad_tracker.sql`) are still in this folder from the very first build, but there is no evidence anywhere later in the transcripts that the Supabase mirror was ever actually applied (`supabase db push`) or written to — the project pivoted to the live-server-plus-IMPORTDATA pattern instead, and the Apps Script triggers were explicitly abandoned because of the timezone bugs above. Treat these files as historical/superseded rather than a currently-running part of the system.
- `README.md` in this folder still describes the *original* Apps Script + Sheet design (Meta + OnlyFinder only, `buildTracker()`, daily Apps Script triggers, Supabase mirror via `pushToSupabase()`). It has not been updated to reflect the live-server/Weekly-sheet architecture that's actually in use, or the additional platforms (OnlyGuider, OnlySeeker, OnlyTraffic) added later. Anyone picking this project back up should treat the README as describing an earlier, superseded design rather than current behavior, and probably rewrite it to match `build_weekly.py` + the Railway server.

## Bottom line

This started as a straightforward "build me this Apps Script tracker" request and turned into a much larger, iteratively-negotiated product: a hosted dashboard with an embedded AI strategist and a separate cloud-agent data analyst, a password-gated multi-page web app, and — running in parallel and ultimately taking over as the primary deliverable — a zero-maintenance Google Sheet backed by a live always-on server. Almost every major turn (Vercel→Render→Railway, Apps Script→live server, "give me a dashboard"→"boss just wants a simple sheet") was a direct, explicit response to something the boss said didn't work or didn't match what he pictured, relayed through a user who was candid about not being technical and needed each explanation in plain, concrete terms.
