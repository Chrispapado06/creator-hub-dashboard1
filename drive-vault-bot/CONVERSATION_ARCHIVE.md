# drive-vault-bot — conversation archive

## Where this came from

On 2026-06-07 the user relayed an idea from "the boss": *"Any time a model uploads content to a Google Drive, it immediately triggers an automation that pulls it from Google Drive and uploads it into the OF vault using the OF API and the tools we have. Let's do it."* Everything in this repo's `drive-vault-bot/` folder grew out of that one message, built almost entirely in a single long Claude Code session that afternoon/evening, then extended twice more (June 8 to wire up the rest of the creator roster, and June 19–20 to fix a large-video upload failure). A closely related but separate Apps-Script project, `drive-folder-sync/`, was spun off on June 9 using the same folder-pattern idea but for plain copy-between-Drive-folders (not OnlyFans) — it's mentioned below for context but is not this project.

## What it actually is

A model (or her editor) drops a photo or video anywhere inside her Google Drive folder — including any subfolder she names herself, like a "script" or scene folder — and within about five minutes that file shows up in her OnlyFans vault. Nothing is moved, renamed, or deleted in Drive; the bot only remembers which Drive file IDs it has already handled so nothing is ever uploaded twice. It runs as a standalone Node ESM script (`bot.mjs` + `config.mjs`), triggered every 5 minutes by a GitHub Actions cron (`.github/workflows/drive-vault-bot.yml`), with a committed `state.json` for dedup — deliberately the same shape as the repo's existing `payout-bot/`, which Claude used as the template from the very first exploration pass.

## Why it had to be a polling bot, not an instant webhook

Before writing any code, the first session mapped what already existed: the dashboard already had a `uploadMedia()` call in `src/lib/of-api.ts` pointed at OnlyFans' vault, and `payout-bot/` already established the "poll on a GitHub Actions cron + dedupe via committed state.json" pattern. The one genuinely new piece was the Drive side. Two findings shaped the whole design before anything was built: the OnlyFans API has no "upload from URL" shortcut and no true native vault upload, so the automation would have to physically download each file's bytes from Drive and re-upload them — ruling out a lightweight, memory-constrained host (a Supabase Edge Function was considered and rejected) in favor of a GitHub Actions runner with real disk. That also meant "immediately" would really mean "within about 5 minutes," which was flagged to the user up front as an honest caveat rather than oversold.

## The vault trick (the central discovery of the whole project)

The biggest surprise, confirmed empirically rather than assumed, is that **OnlyFans does not allow anything — not this bot, not any tool, not even the official API — to upload straight into a creator's vault.** A raw upload only lands the file in CDN limbo. The only documented way to make media persist in the vault is to attach it to a post or message and then delete that post; OnlyFans keeps the media as a side effect. Claude proved this out live on Marissa's real account on June 7 rather than taking the docs' word for it: it uploaded a test image, confirmed it did *not* appear in her vault, then built and tested the actual workaround — upload to the OnlyFans CDN, attach the media to a post scheduled roughly 10 months in the future (so it can never go live and no fan is ever notified), and delete that post within the same second. The vault keeps the media; the post never existed as far as any subscriber is concerned. This is the mechanism still in production today (`uploadToVault()` in `config.mjs`).

That test also surfaced a second, unrelated bug worth recording: the dashboard's own `uploadMedia()` in `src/lib/of-api.ts` posts to `/{acct}/vault/media`, a path that 404s on the live API — meaning that "upload to vault" button in the dashboard UI has likely been silently broken for a while. This bot deliberately does not use that dead path; it was flagged to the user as a separate issue to fix later, and the README carries a note pointing at the working flow to port over if that dashboard feature is ever repaired.

## Design decisions made along the way, and why

A few choices came up mid-build and were changed based on what the user actually wanted, not just what was easiest to code:

- **Files stay exactly where they're dropped.** The bot's very first version moved a file into a "Posted" subfolder once uploaded (mirroring how a person would visually confirm "this one's done"). The user then asked whether new subfolders — like a "script" name — inside a creator's folder would also get picked up. Claude pointed out the conflict: recursing into subfolders while also moving files out of them would wreck whatever organizational scheme the team was using. The user's call was to leave files in place and dedupe purely via the internally-tracked file ID, so the bot was rewritten to walk the whole folder tree (depth-guarded to avoid infinite loops) and drop the file-moving step entirely. This also had a nice side effect: the Google service account only needs **Viewer** access now, not Editor, since it never touches Drive content.
- **Access model for the Google service account.** When the user offered to hand over a personal Google login, or floated creating a throwaway Gmail for Claude to drive via the (then-unconnected) Chrome extension, Claude declined to log into a real account or auto-pilot key creation, laying out plainly which steps are inherently the user's to click (creating the account, any CAPTCHA/phone verification) versus which it could do once credentials existed. The user ultimately did the Google Cloud service-account setup themselves via a click-by-click walkthrough, then pasted the service-account email and JSON key into chat for Claude to wire in — with an explicit warning each time that the key should be treated like a password and not reused or shared elsewhere.
- **Pushing to GitHub without touching the user's other work-in-progress.** By the time this was ready to ship, the user's working tree had ~10 unrelated modified files (ChatBadge, chat.ts, etc.) and the local branch was 11 commits behind GitHub. Rather than risk a normal push/pull colliding with that WIP, Claude committed only the new bot files locally, cherry-picked just those commits onto a clean copy of the latest `main` in an isolated location, pushed that, and discarded the temp copy — leaving the user's uncommitted work completely untouched throughout.
- **Per-creator OF account IDs are reused from `payout-bot/config.mjs`**, so no new mapping had to be invented — this bot's `DRIVE_MAP` in `config.mjs` intentionally lines up with the existing payout config's `account_id`s per creator.

## The large-video failure and how it was actually fixed (June 19–20)

Once real content started flowing through live folders, the automation's Telegram alerts started reporting upload failures for Blue Bear's and Julie's videos — Blue's biggest clips were 90–97 MB, Julie's custom videos ran 300–676 MB. The user's reaction was blunt: "we HAVE TO FIX IT." Claude dug into the OnlyFans API's full OpenAPI spec (rather than guessing) and found the real cause: the direct multipart upload path used by the bot is hard-capped at 100 MB by Cloudflare, full stop — no amount of retrying gets past it. The spec also showed the fix: OnlyFans' upload endpoint accepts a `file_url` field and an `async` flag, letting OnlyFans pull the file itself from a link rather than have the bot push the bytes through Cloudflare, and that path supports files up to OnlyFans' real ceiling of 1 GB.

Before committing to that architecture, Claude also found and tested an undocumented-sounding `POST /media/vault` endpoint that claimed to upload straight to the vault (which would have let the whole scheduled-post-and-delete hack be retired entirely). It turned out OnlyFans was having a platform-wide upload outage at that exact moment (both the old and the new endpoint were both returning 503 while `GET /me` worked fine), so that couldn't be live-verified and the decision was made to keep the proven scheduled-post mechanism and only upgrade the *upload* step — lower risk, since it left the working small-file path completely alone.

The fix that shipped: files ≤90 MB still upload directly (unchanged); anything larger is staged to a private bucket, handed to OnlyFans as a short-lived (1-hour) signed URL, pulled asynchronously, and polled until OnlyFans reports the transcode finished, at which point the temp copy is deleted. Files over the hard 1 GB OnlyFans limit are recorded once and flagged rather than retried every 5 minutes forever. This code path touches a live revenue system and private content, so before shipping it Claude ran an adversarial multi-reviewer pass against it and fixed the real bugs that turned up (one confirmed high-severity issue was that the async-upload response parser read `prefixed_id`/`polling_url` at the wrong nesting level).

The staging bucket itself changed providers mid-build: it first went into a private **Supabase** bucket, but the user balked at needing to pay for Supabase Pro just for temporary staging space, so Claude re-pointed the same signed-URL mechanism at **Cloudflare R2** instead — chosen because the team already uses Cloudflare, R2's free tier comfortably covers this (10 GB storage, and the bot deletes each staged file the moment OnlyFans finishes pulling it, so real usage stays near zero), and critically R2 has no egress fee, so OnlyFans downloading the staged file costs nothing. This is the version running today: `aws4fetch` signs presigned R2 PUT/GET requests, and the four `R2_*` GitHub secrets are optional — if they're absent, small files still upload fine and large ones are simply flagged instead of silently failing.

## Current status

The bot is live and has been running unattended since mid-June. `state.json` (committed back to the repo after every run, hence the long tail of `drive-vault-bot: update state.json [skip ci]` commits in the git log) shows 370 processed file entries as of the last run on 2026-07-15: the real ongoing usage is almost entirely **Julie** (245 files) and **Blue Bear** (124 files) — the creators whose teams actually adopted the workflow day to day — plus the single original Marissa test file and two files flagged as over the size limit. Emma, Meg, and Marissa are wired in and technically live but show no real recurring usage in the state file beyond the initial test, meaning either those teams haven't started using their folders yet or content isn't being routed through them.

## Known gaps / things not done

- Only 5 of the (implied larger) creator roster are wired into `DRIVE_MAP`; adding a new creator is a quick, well-worn process (share folder → send link + name → Claude adds one config row and pushes) but still requires that manual per-creator step — there's no self-serve "any folder named `<Creator> — ...` auto-maps" convention, though Claude offered to build that and it was never taken up.
- Drive-side "category" subfolders (e.g. a script name) are cosmetic only — everything lands in one flat OnlyFans vault. A "Drive folder categories become named vault albums" enhancement was discussed (OnlyFans does support vault lists) but never built.
- The Discord "new content landed → ping the team to organize/review it" integration, sketched against the existing shift-approval Discord bot pattern, was scoped but never implemented — it stalled waiting on Discord user IDs for staff members not already in that bot's config.
- The dashboard's own `uploadMedia()` in `src/lib/of-api.ts`, pointed at the dead `/vault/media` path, is still broken as far as this archive shows; it was flagged to the user as a follow-up but this project's fix was never ported back into the dashboard UI.
- A couple of test-upload copies were deliberately left sitting in Marissa's real vault from the June 7 live testing; the user was told to delete them manually so they don't get sent to a fan by accident — whether that housekeeping was ever done isn't recorded in these transcripts.
