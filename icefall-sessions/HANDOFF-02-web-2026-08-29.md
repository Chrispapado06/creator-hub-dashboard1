## Next piece of work: the video block — RESOLVED, ready to build

**This section was "ON HOLD, DO NOT BUILD" for about an hour. Decision 16
resolved it.** The history is kept because the shape of the answer matters.

**What happened:** decision 14 put a company's film on both their own page and
their mountain blocks. Decision 15 said one film per mountain, stored on
`company_mountains`, with no company-level film. Each was coherent alone; together
they left the company page with no film to render. Session 04 spotted it.

**Decision 16 — the resolution.** The company page shows **their films, listed by
mountain**: it gathers what the operator has already published across their
placements and offers them as a small set a climber can pick from ("Everest
2026", "Denali spring"). Nothing new is stored. No company-level film is
introduced. Decision 15 stands untouched.

So the block is **a small list sourced from `company_mountains`**, not one embed
fed by a company-level field. Session 03 has the film columns on that table.

### ⚠ The ordering constraint — read before you start

**Do not add `video` to `SECTION_IDS` until the block actually renders.**

`previewProtocol.ts` carries a long note on this at the list itself. In short: a
declared id with no element behind it measures as `not-found` on every pass
forever, and `not-found` is defined as the loud case the editor must treat as an
error. Declaring it early would show Session 04 a permanent, unfixable error
about a section nobody can build yet.

That is the same ordering failure three times over — an editor control that
writes into nothing, a page block no data can reach, and a declared id with no
section. **The id and the block land in the same change.**

### Constraints, all agreed and unchanged by decision 16

- **Keep the click-to-load pattern** used by `tripDetail.ts`: nothing is
  requested from `youtube-nocookie.com` until a climber presses play, so the
  page carries no third party for everyone who does not watch. Do not regress
  this for a new section.
- **Keep the honest empty state.** The page currently renders
  *"No video has been published by this operator."* — a true and useful
  statement. A section that vanishes is worse than one that says nothing is
  there.
- **`videoId` must be hard-validated** (`^[A-Za-z0-9_-]{11}$`) wherever it is
  stored, before it is ever used to build an embed URL. **Already done on the
  draft side:** `applyCompanyDraft` in `previewProtocol.ts` now refuses `videoId`
  and `videos` outright, so a preview shows published films or the empty state
  and never an embed assembled from something typed into an editor seconds ago.
- When the block lands, add a `video` id to `SECTION_IDS` **and** to
  `SECTION_TAB` in `useCompanyPreview.ts` — in the **same change**, per the
  ordering constraint above — and tell Session 04. The contract stays
  `protocolVersion: 1`: adding an id changes the list, not the shape, and 04
  treating an unrecognised id as an error is the mechanism working. Bump to `2`
  only if the message shape itself changes.

**Ordering rule now in the constitution:** a section may not appear in an editor
before the surface it edits can render it. Session 04's "Promotional film" row
already ships and is currently a phantom — an operator can set a film, the row
goes green, nothing renders anywhere.

Note the rule cuts both ways, which is the lesson of the hold above: shipping a
block that no data can reach is the same defect as shipping a control that
writes into nothing. Whichever way the owner resolves 14-vs-15, the film's
storage and its rendering surface have to be decided together — that is what
went wrong, and it went wrong because two coherent answers were given on two
separate turns and never held up against each other.
