# ICEFALL — project conversation archive

This document reconstructs the working history of the ICEFALL app family from local Claude Code memory notes (nine project-memory files, listed at the end) and the raw session transcript that built almost all of it: session `29e98fe8-2777-45d5-b28c-583d1065011b`, running continuously from 2026-08-15 17:04 UTC to 2026-08-22 15:26 UTC (the point this archive was written, mid-verification of the most recent feature — see "Where the transcript actually stops" below). That one session is roughly 78 MB and 13,500 transcript lines; a handful of other sessions mention ICEFALL only in passing (memory-file listings, directory listings) and add no new facts. A separate, much older and unrelated project — `theicefall-shopify/`, a Shopify apparel-store redesign for the same brand name — is **not** covered here; it has its own history and its own memory note (`project_theicefall_shopify`).

## What ICEFALL is

ICEFALL is a luxury, mobile-first product for outdoor athletes and mountaineers, pitched — in the README's own words — to "feel credible next to a €1,000 technical jacket." The product spans discovery, training, live activity tracking, and a two-sided marketplace connecting athletes with certified mountain guides and expedition operators: **Discover → Plan → Train → Perform → Explore → Achieve**. It is entirely unrelated to the rest of this repository's UNCVRD OnlyFans-agency tooling; it shares nothing but the monorepo it happens to live in.

Two platform decisions anchor everything else. First, the whole family is built as **Vite + React web apps, not Expo/React Native** — a deliberate choice made knowing this Mac has no Xcode and therefore no iOS simulator to verify a native build against; Capacitor wraps the web code later with no rewrite needed. Second, the athlete app is **dark-only by design** ("a light mode would dilute the brand, not extend it"), running on real MapLibre GL terrain (OpenFreeMap vector tiles + AWS terrarium elevation, both free and keyless) and real Wikimedia Commons photography rather than a stock-photo service — Unsplash's own API and search now require auth, so Commons (which mirrors CC0 Unsplash imports) stands in.

## Why one product became six folders

ICEFALL did not start as six folders. It started as a single package (`icefall-app/`, built 2026-08-15) with every screen — including guide browsing and booking — running against local fixtures. The split happened in stages, each one driven by a real requirement rather than upfront architecture:

- **`icefall-app/`** (port 5190, launch config `icefall`) — the original and remains the athlete-facing product. All 16 initial screens, later many more, built against mock data with a single seam (`src/services/repository.ts`) for swapping fixtures for a real API.
- **`icefall-supabase/`** (created 2026-08-17) — when the user asked for a real backend so guides and expedition companies could message clients in-app, the schema went into its own top-level folder "because two apps share one database," not because either app owns it. It now serves three consumers (app, admin, guide).
- **`icefall-admin/`** (created 2026-08-17, port 5192, "ICEFALL Operations") — built the same day as the backend, specifically so **client lists, revenue figures and internal notes never ship inside the bundle an athlete downloads to their phone**. It is a separate codebase, separate build, separate deploy, its own login — "the only thing it shares with the [athlete] app is the database." Visually it deliberately does *not* look like the athlete app (light, dense, data-forward, Pipedrive-style) so nobody mistakes a staff screen for a customer one.
- **`icefall-guide/`** (created 2026-08-17, port 5193, "ICEFALL Guide") — described in-session as "the missing side of the marketplace": a third, separate app for guides and expedition companies themselves — signup, document-based verification, a "Today" queue of unanswered enquiries, "Openings" (bookable dates with a mandatory "the client must already be able to…" line), and their own Profile/Enquiries views. It started as a plain screen set and was later rebuilt wholesale to match the athlete app's exact design tokens, `PhoneShell`, tab bar and primitives once the user said it should "feel like ICEFALL, and be a phone app" — copied wholesale rather than approximated.
- **`icefall-shared/`** (created 2026-08-18) — once money entered the picture (guide payouts, ICEFALL's commission, refunds), the risk of three apps quietly disagreeing about what a client owes became "the worst possible bug in this system." `money.ts` is the single canonical file; it is not a real workspace package (no npm workspaces, no symlinks) but a small manual `npm run sync` script that copies the file verbatim into `icefall-app/src/money/model.ts`, `icefall-guide/src/money/model.ts` and `icefall-admin/src/money/model.ts`. Edit only the source in `icefall-shared/`, then re-run sync.
- **`icefall-web/`** (created 2026-08-18, port 5194) — the desktop half. Not a stretched phone layout but a genuine Airbnb-style marketplace shell (sticky nav, centred content column, listing grids, hover states) sharing the same design tokens and the same `money.ts` model as the phone apps. It was rebuilt from scratch the following day (2026-08-19) after the user rejected the "browse guides, add flights at checkout" pattern in favour of a **search-first** front page — pick a mode (Guide only / Flights + Guide / Whole package), destination, dates and party *before* seeing any results.

The common thread across every split: keep internal/business logic and data (verification queues, commission math, revenue, client identities) structurally out of the surface an athlete's phone downloads, while letting genuinely different platforms (phone vs. guide-facing phone vs. desktop marketplace vs. staff back office) each get a layout suited to what they actually are, rather than one app wearing four hats.

## Locked decisions and constraints (do not re-litigate)

These are documented in-repo (READMEs, code comments) and in memory precisely because they are easy for a future session to "fix" by accident:

- **Maps.** `TerrainMap` runs MapLibre GL pinned to **`^5`** — v6 silently breaks it (the tile worker never initializes, so vector tiles are never requested, with no error at all, while raster elevation tiles load fine and mask the problem). Only treat map errors *without* a `sourceId` as fatal; use the `load` event, never `isStyleLoaded()`, as the readiness signal. `RouteMap` (procedural contours) remains the offline/error fallback so an activity is never blocked by a map.
- **Imagery.** All photography comes from Wikimedia Commons at runtime, sourced from each mountain's own Wikipedia/Wikidata entry — never a stock library, never a generic "mountain photo." Licences are tracked in `public/img/CREDITS.md`; some require public attribution and need re-verification before any commercial launch.
- **Measurement honesty (the tracker's core constraint).** Every metric resolves to a value *or* an explicit reason (`no-sensor`, `no-gps`, `indoor`, `not-connected`, …) — the UI renders the reason, never a zero. Calories are the one modelled value and are always labelled "est." ICEFALL Points are hard-capped (5 h, 60 km, 3,000 m vertical, 5-day consistency) specifically so the reward system can never make it rational to keep going when someone should stop.
- **Mockup-fidelity honesty constraints.** When Home, Routes and the subscribe flow were rebuilt to supplied user mockups, a recurring rule applied: anything the mockup showed that ICEFALL cannot actually measure or does not actually have gets removed rather than faked. Confirmed, deliberately-not-reproduced examples: a fake "82% weekly readiness" (only *today's* readiness exists), a fake "EXPEDITION READY" verdict (`mountainReadiness.ts` is "deliberately hostile" to that reading), fabricated "4/6 group" / "5 going" counts (there is no backend — the real number is always 1), a "People nearby" list of invented athletes (the real array is `[]` and "MUST STAY EMPTY until there is a real backend" — a fabricated nearby partner is "a hazard, not a placeholder"), star ratings and comment counts on routes (no users, no backend — and a popularity number on a mountain route reads as an unearned safety signal), and posed "356 people liked this" style social proof throughout.
- **Subscription paywall is inline-only.** `UpgradePrompt` / `LockedPreview` explicitly forbid a modal, bottom sheet, or interstitial paywall — no popup, never blur the athlete's own data, nothing that worked yesterday gets withdrawn, no countdown/scarcity pressure. This was deliberate and brand-critical; when the user asked for a "paywall sheet" it was built inline instead. Plans are Base (free) / Pro (€15/mo, €144/yr) / Expedition (€29/mo, €278.40/yr — the elite tier), with roughly a fifth of the gated features flagged `notYetEnforced` (built but not actually withheld) until real billing exists, because withholding something with no way to pay for it isn't honest gating.
- **Lock-screen live-activity widget is native-only, permanently.** A PWA fundamentally cannot show distance/speed on the lock screen — iOS suspends a backgrounded tab (GPS and timers stop) and there is no Live Activity/Dynamic Island web API; Android needs a real foreground service. The only real path is Capacitor → a background-geolocation plugin → iOS ActivityKit (Swift) / an Android foreground-service notification. The code can be written on this Mac; it cannot be compiled or verified here (no Xcode, no Android Studio) — the user has to build it.
- **Coach is scripted by default and spend-capped.** `askCoach()` only calls a real model when `VITE_COACH_ENDPOINT` (a **server-side** proxy) is set — never a client-side API key — and falls back to the scripted engine on any error so chat never breaks. When it does call a model, `src/coach/budget.ts` caps it: 8 credits/day (reset on the local day, not monthly — a monthly pool front-loaded by one enthusiastic afternoon would leave the coach dead for weeks), with an invisible monthly $1.00 hard backstop underneath. The visible unit shown to athletes is "credits," deliberately never dollars, so nobody starts pricing their own questions. This client-side counter is explicitly documented as a courtesy stop only — the real limit has to live in the server-side proxy.
- **Expedition operators, gear and course content stay fictional/sample-only** until the business is real: `services/operators.ts` entries are all `sample: true` with no prices or ratings shown (those are exactly the numbers someone would book on); ICEFALL's own apparel renders as typographic tiles rather than photographs, so a placeholder never gets mistaken for a real product; avatars are initials, never photographs, so no fictional community member wears a real person's face.

## Bugs and regressions fixed along the way

- **The Coach chat router gave confidently wrong answers.** Its eight keyword rules were unanchored regexes: `/eat/` matched inside "w-EAT-her" (so a weather question returned the nutrition answer and the actual weather rule was unreachable for its own keyword), and `/ramp/` matched inside both "c-RAMP" and "c-RAMP-on" (so a calf cramp and crampon *technique* questions both returned "don't add volume this week"). 0 of 7 test questions routed correctly; anchoring every regex with `\b` fixed all 8.
- **Today vs. Chat contradicted each other.** The dashboard's `briefing.ts` could downgrade a hard session (`easeOff`), but chat never read that flag, so it could tell someone to "hold the efforts honest" on a day the dashboard said rest. Chat now defers to the same decision.
- **A goal's countdown could silently break.** `daysUntilLocal()` needs a `YYYY-MM-DD` key, but goals stored a full ISO instant; the coach reported "date not set" for goals that had a real date. Fixed by converting via the local calendar day rather than slicing the UTC string, since slicing shifts a day for anyone west of Greenwich.
- **A real money bug caught by the test suite, not a code review.** `refundFor` counted fractional days rather than calendar days: a client cancelling exactly 60 calendar days before departure, but 59.5 fractional days because of the time of day, silently dropped from the 100% refund tier to 50% — a difference the client could never have predicted or explained. Caught by one of 39 (later 58) money-model tests before it ever reached a real booking.
- **Weekly readiness and season logic had a wrong-scale bug.** `assessPeak(elevation, lat, lon)` needs longitude, not just latitude — the plain-latitude rule returned "summer" for Nepal, which is the monsoon and the worst possible advice, while the Karakoram genuinely is in its summer window at the same latitude band. Both are now special-cased.
- **Route photography was pulling in the wrong images.** `resolvePeakGallery` was returning entire Commons *categories* rather than photos of the peak itself — cards and detail pages showed a named climber "at the Breithorn," a Mont Blanc book plate captioned "Matterhorn," a funicular-carriage interior, and similar mismatches. Fixed with `fileIsAbout()` (the filename must contain every word of the peak's name) plus an explicit block-list (fondue, hotel, portrait, …); a stale, never-downloaded gallery manifest (`public/img/_gallery.json`) was also deleted outright.
- **A self-inflicted duplicated-work incident (2026-08-16).** An 8-agent background Workflow building the subscription/growth system was checked with `ps`, appeared to have no running process, and was declared dead — so its work (`tiers.ts`, the upgrade funnel) was rebuilt by hand. The workflow had actually completed successfully in the background the whole time; both versions then raced on disk. The result was reconciled (mostly the hand-built `tiers.ts`, the workflow's version of everything else, including `readinessTest.ts`, `Pricing.tsx`, `UpgradePrompt.tsx` and `ShareReadiness.tsx`, none of which had been built by hand at all) at the cost of two runs' worth of work for one outcome. Logged lesson: check the filesystem, not the process list, before declaring a background run dead. The same session separately caught, at that same audit, that the Elite tier bought literally nothing (all five of its differentiators were `comingSoon`) and that the free Coach's 3-conversation limit was entirely unenforced — both were fixed in later sessions (Elite gating is still partially `notYetEnforced` by design; Coach metering was wired up around 2026-08-20/21).

## Current status by subsystem

**icefall-app (phone, athlete-facing).** The largest and most complete piece. Full navigation (Home · Activity · Coach · Explore · Profile), a framework-free live activity recorder (GPS via `navigator.geolocation`, heart-rate via Web Bluetooth GATT, with a clearly-labelled indoor simulator), generated per-goal training plans, a peak-discovery system covering roughly 4,200 bundled Alpine peaks plus live worldwide Overpass lookups, and an offline-capable build (`vite-plugin-pwa`, verified with the dev/preview server killed: cold load works, a never-visited deep link still renders, 132 precache entries). Crash-safe activity recording (survives the app being closed mid-session) is done and verified. The Coach is roughly 9,200 lines of engine under ~5,700 lines of screens, now unified behind one `useCoachContext()`; its nutrition engine (`nutrition.ts`, 1,740 lines) is written but wired to nothing — the Nutrition screen still renders a fixture. Home and Routes/Explore were both rebuilt to supplied user mockups in the last week of the transcript, each pass explicitly auditing which mockup elements were real vs. fabricated (see above). The subscribe flow was rebuilt to a mockup on 2026-08-21 with an honest "no card needed" trial screen, deliberately not reproducing the mockup's fake saved Visa card. The lock-screen widget is still unscaffolded — no `ios/`/`android/`/Capacitor config exists yet, only the plan to add it.

**icefall-admin (staff back office).** Six-plus screens: Dashboard (booking value, pipeline, "awaiting reply" counter), a drag-and-drop Deals/Pipedrive board (drag verified working, resets on reload — there is nowhere to persist it to yet), Contacts, Conversations, Partners, Transactions, a guide/company Verification queue (approve/decline with a mandatory reason field, badge language deliberately limited to "documents checked by ICEFALL," never implying the issuing association was contacted), and Referrals (fees owed/disputed/unreported, built for the referral commission model). Runs locally on port 5192; has no Supabase client wired in at all yet (no `@supabase/supabase-js` dependency, no `backend/` folder) — it is UI and local state only, ahead of the database connection.

**icefall-guide (guide/company-facing phone app).** Signup captures documents up front rather than verifying after the fact — "an unverified guide who can already talk to clients is the failure worth designing out." Screens: Auth, Today (unanswered enquiries with wait times, open dates, earnings), Openings (bookable dates with route, price, seats, and the mandatory readiness line), Enquiries, Profile, Verification, Payouts. Rebuilt to match the athlete app's exact `PhoneShell`/design tokens rather than a bespoke look. Like icefall-admin, it has no Supabase client wired in yet — local state only, on port 5193.

**icefall-web (desktop marketplace).** Search-first trip builder: a mode toggle (Guide only / Flights + Guide / Whole package) plus objective, origin (for flight modes), dates and party feeds into a `/plan` results screen and a `/book/:id` confirmation-only page; search state lives in the URL. A zero-dependency Node server (`server/`, port 8788) added a real, keys-server-side data layer on 2026-08-20 — Duffel for flights, LiteAPI/Nuitée for hotels — structured so the app is "real" the moment a key is added to `server/.env`, with a graceful `{connected:false}` fallback to labelled demo data when no key is present or the server is down. Booking/ticketing, payment and the EU/UK "package organiser" legal layer (ATOL-style bonding) are explicitly not built — search only. By deliberate decision (2026-08-19), flights/packages stay desktop-only and are not being added to the phone app. Also has no Supabase client wired in yet, and — like icefall-admin and icefall-guide — has never been deployed (no `.vercel/` folder exists in any of the three; only icefall-app has ever run `vercel --prod`, and even that deploy is push-from-local, since none of the six folders are tracked in this repo's git history at all — every one of them still shows as untracked).

**icefall-supabase (shared backend).** Two migrations exist: `20260817120000_icefall_foundation.sql` (profiles/roles, guide/operator profiles, threads/participants/messages, full RLS) and `20260818090000_chat.sql` (the guide/company messaging-gate logic — a guide thread only unlocks after a paid booking, a company thread only after a qualified enquiry, closing the "take this off-platform" leak structurally rather than with a warning). 15 RLS attack tests run on PGlite (real Postgres compiled to WASM, since this Mac has no Docker/local Postgres) and must all be refused — `npm test` inside `icefall-supabase/`. Deliberate schema invariants: no UPDATE/DELETE policy on messages for anyone including admin; `guide_profiles.credentials_verified` carries `CHECK (= false)` (removing that constraint is the deliberate act that turns real verification on); signup always creates an `athlete`, never a higher role. **Not connected to a live project anywhere** — none of the four consuming apps has a `.env.local`, and only `icefall-app` even has the Supabase client code (`src/backend/client.ts`, which returns `null` and runs on localStorage when unconfigured — a supported state, not a bug). Getting it live needs a Supabase project plus `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` (not `_ANON_KEY` — the wrong name fails silently) dropped into each app.

**icefall-shared (money model).** One file, `money.ts` (478 lines) plus `money.test.ts` (227 lines, 58 assertions as of the last sync), covering integer-cent arithmetic end to end for a three-way split (client pays, guide receives, ICEFALL keeps commission), with rounding remainders deliberately left with the guide rather than the platform. Synced by a manual `npm run sync` script, not a real package — copies verbatim into the three consuming apps' `src/money/model.ts`. No payment processor is connected anywhere; the file is explicit that "nothing in this file moves money," it only defines the rules a processor will eventually be driven by.
