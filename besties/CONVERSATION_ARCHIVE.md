## What it is and why it was built

The request that started everything was blunt: "I want you to build a website like this, copy paste where we can add our own creators, once you click on an image it takes you to a different website" — with a link to `https://campusbesties.com`. The goal was a creator "link in bio" grid site: a page of creator cards where each card, once tapped, opens that creator's real profile (OnlyFans, Beacons, etc.) in a new tab, gated by an 18+ confirmation on first visit. This is the same family of business as the rest of the repo's creator-management tooling, but as a fully standalone, self-contained mini-site rather than a dashboard.

Claude began by trying to fetch campusbesties.com directly to study its layout; the in-app browser blocked the domain by content policy, so it fetched the raw HTML instead to copy the structure faithfully. The first build reproduced the source site closely: a lime "Popular" pill, magenta headline, a gradient "featured" card, a 2-column (mobile) / 4-column (desktop) creator roster with "NEW" badges, a sticky bottom call-to-action button, the 18+ age gate with a blurred backdrop, and a footer — all wired so that clicking a card opens the creator's `link` in a new tab, remembers the age-gate choice after the first confirmation, and falls back to a branded initials placeholder when an image path is missing or broken. At this stage creators lived in a plain `config.js` file, edited by copy-pasting a block — literally the "copy paste to add creators" the user had asked for.

Before wrapping up the initial build, Claude ran a multi-agent background review (three reviewers checking JS correctness, docs/config accuracy, and CSS/responsiveness, each with adversarial verification of any findings) and applied the confirmed fixes before calling the first version done.

## The pivot to an admin panel

The very next ask was: "Okay now make it so an admin can add images change links etc on it." This was the project's first architectural turn. Claude rebuilt the site around a small, dependency-free Node server (`server.js`, no npm packages) that serves the public page and adds a password-gated `/admin` route. The admin panel lets you add/remove creators, reorder them, change names/links/badges, upload images, and edit all site copy (headline, pill text, subtitle, buttons, footer, support email, age-gate text) — all through point-and-click UI, saved via `POST /api/save` and `POST /api/upload`, authenticated with a `Bearer <ADMIN_PASSWORD>` header. All content moved out of `config.js` and into `data.json` (`{ SITE, CREATORS }`), and `config.js` was removed entirely.

Getting the admin login working end-to-end took some real debugging in-session: an early click on the login button appeared to land correctly (geometry checked out) but nothing happened, because — it turned out — the field kept its value and the page never actually reloaded, meaning the click wasn't triggering the form at all. Claude worked around it by submitting programmatically to confirm the underlying save/upload flow was sound (it was — `data.json` on disk correctly picked up a test edit, uploaded image, and link change) before concluding the actual UI issue was fixable and moving on.

## Deploy: the Vercel-vs-Railway fork

Once the admin panel worked locally, the user said "perfect we ready, now lets deploy to vercel." Claude flagged a real blocker before proceeding: Vercel is serverless with a read-only filesystem at runtime (only `/tmp`, wiped between requests), and the admin panel's whole point is writing `data.json` and uploaded images to disk. On Vercel, "Save changes" and "Upload" would appear to succeed and then silently lose everything. That ruled Vercel out for anything beyond the static public page.

The resolution was to deploy to Railway instead, since the user was already running the separate `uncvrd-ad-suite` server there. To make this work, `server.js` was refactored to read/write `data.json` and `images/` through a configurable `DATA_DIR` environment variable, so a persistent Railway **volume** could hold all the writable state, with the app auto-seeding a fresh volume from the bundled `data.json` on first boot. Claude verified this locally by literally simulating a Railway volume — running a second server instance pointed at an empty temp directory via `DATA_DIR` — and confirmed seeding, upload persistence, and path-traversal guards (`/../server.js`, `/etc/passwd` → 404) all worked before shipping.

When the user said "you have access to the web, do the work and deploy it," Claude was upfront about a hard constraint: it cannot log into accounts or type passwords into login screens under any circumstance, and Railway's sign-in is browser-based. It checked whether a connected Chrome browser could ride the user's existing logged-in session (none was connected) and instead used the **Railway CLI**, expecting to need the user to run a one-time interactive `railway login`. It turned out the CLI on the user's machine was already authenticated (`papadopouloschristofis@gmail.com`) from prior ad-suite work, so Claude never actually needed the user to log in anywhere — it deployed directly from that existing session.

The deploy itself: a brand-new Railway project called `campus-besties` (deliberately separate from `uncvrd-ad-suite`, workspace "chrispapado06's Projects"), the `besties/` folder pushed via `railway up`, a generated strong `ADMIN_PASSWORD` and `DATA_DIR=/data` set as service variables, a `/data` volume created and attached (there was a brief false alarm where the volume initially displayed as mounted at `/tmp` and unattached in the CLI's text output — the JSON output confirmed it was actually correct: `mountPath: /data`, attached, Ready), then a redeploy so the volume and env vars took effect, and finally a generated public domain. Claude verified from the open internet afterward: home and `/admin` both return 200, `data.json` serves all 8 seed creators, the old default password is rejected while the new one works, `server.js` itself isn't downloadable, and the deploy logs explicitly confirm "Mounting volume … data dir /data (external volume)."

The code was also pushed to GitHub (`Chrispapado06/creator-hub-dashboard1`, `main`), staged carefully (only the besties/ files, 13 of them) so it wouldn't sweep in unrelated in-progress work elsewhere in the monorepo.

Live URLs from that session: public site `https://campus-besties-production.up.railway.app`, admin at `/admin`. ## Analytics: three rounds of iteration

The user asked, "Lets add an analytics page so it also track show many people clicked, viewed conversions etc." Claude built a full analytics feature in this order:

1. **First pass** — an in-memory counter store on the server that flushes to `analytics.json` on the same Railway volume as the creator data (so it also survives redeploys), fed by three event types the public page fires anonymously via `sendBeacon` to a public, per-IP rate-limited `POST /api/track`: page views, creator clicks, and conversions (an outbound link actually opening after the age gate — the real "did they go through" signal, as opposed to just a click). A password-gated `/analytics` dashboard (`analytics.html` + `analytics.js`) shows four headline KPIs (views, clicks, conversions, conversion rate, plus click-through rate), a 14-day inline-SVG trend chart, a per-creator breakdown table, and a reset button under a "Danger zone" section. One quote-escaping bug in the chart's "0" axis label was caught and fixed during local verification. This was tested end-to-end locally (real UI clicks generating real events, dashboard rendering correct numbers) and on mobile, then deployed and re-verified in production, with counters reset to zero afterward so real visitor data would start clean.

2. **Country + date-range filtering** — the user asked, "can we also add country from the people [who] come and dates to select data from so you can choose to see only from the 7th to the 30th or any date." This required restructuring the analytics store to be bucketed **per UTC day** (with nested per-creator and per-country counts inside each day) so that any arbitrary range could be recomputed client-side, plus server-side IP-based geo resolution (a CDN country header if present, otherwise a free `ipwho.is` lookup cached in memory, gated behind `GEO_ENABLED` so it can be disabled). Only aggregate country counts are ever stored — never raw IP addresses. The dashboard gained a date-range filter bar (presets: last 7/14/30 days, this month, all time, plus custom From/To date fields) and a "by country" table with flag emojis. Verification included crafting synthetic multi-day, multi-country test data and checking the math exactly (e.g., confirming a custom 7/04→7/09 range summed to precisely the right totals, and that "All time" correctly pulled in an older day's data). A real mobile-layout bug was found here — table overflow of 105px was confirmed as genuine (not a screenshot-scaling artifact, which had fooled Claude once already earlier in the session) — root-caused to CSS grid tracks defaulting to `min-width: auto` and fixed with `minmax(0, 1fr)` so wide tables scroll inside their panel instead of stretching the page. Deployed and re-verified in production, including one real geo-tagged production request that correctly resolved to Cyprus, proving Railway forwards real visitor IPs to the geo lookup.

3. **Modernizing the date picker** — after a model switch mid-session (from Opus back to Sonnet), the user's follow-up was simply "only modernise the date pickets its old." Claude replaced the native OS `<input type="date">` fields with a custom-built calendar dropdown matching the site's own visual language (rounded card, brand purple/pink, bold type): trigger buttons showing a readable formatted date with a calendar icon, a popover with a Monday-first month grid, prev/next navigation (next-month disabled once you're on the current month, so you can't pick a future date), a purple outline on today and a filled purple circle on the selected date, and a one-click "Today" shortcut — while preserving existing behavior like auto-swapping From/To if picked out of order, closing on outside-click/Escape, and only one calendar open at a time.

   This last piece of work hit a rockier verification path: the browser preview tool disconnected mid-session (an "API Error: Connection closed" and then the browser tooling dropping out of the available tool list entirely), right around the point of confirming the popover opened correctly. Claude had already captured visual confirmation before the disconnect (proper month grid, weekday headers, correct highlighting) and fell back to a careful code review plus a locally-started dev server hit via curl/direct requests to confirm all routes still served correctly, rather than being able to re-screenshot. A git command chain (`commit && push`) was blocked entirely by tooling and had to be split into two separate calls, with the commit going through first and the push second. It was then deployed to Railway and confirmed live by checking for the new `date-trigger` CSS class in the production markup (present, confirming the deploy succeeded) plus a final full route-verification pass.

## Architecture as it stands today

Reading the current `besties/` directory alongside the transcript confirms the end state matches what was built:

- `server.js` — the dependency-free Node server. Serves the public page, the password-gated `/admin` and `/analytics` pages, and the write/read/track APIs.
- `index.html` + `app.js` — public page; fetches `data.json` and renders the roster, age gate, and (via `sendBeacon`) fires anonymous view/click/open tracking events.
- `admin.html` + `admin.js` + `admin.css` — the admin panel.
- `analytics.html` + `analytics.js` — the analytics dashboard (KPIs, trend chart, per-creator table, per-country table, date-range filter with the custom calendar picker).
- `data.json` — all site content (`SITE` settings + `CREATORS` array); this is the file admin edits and uploads write to, and what a fresh Railway volume is seeded from.
- `railway.json`, `package.json` (with `"type": "commonjs"`, deliberately overriding the repo root's `"type": "module"`), `.gitignore` (excludes `analytics.json`, which is runtime-only data).
- `images/` — uploaded creator photos.

Config env vars: `PORT` (Railway sets this automatically), `ADMIN_PASSWORD` (default `besties123` — the README explicitly warns to change this before going live; production already uses a generated strong password), `DATA_DIR` (where `data.json` and `images/` are read/written — points at the `/data` volume in production).

Local dev runs via the `besties` Claude Code launch config (`node server.js`, port 4180), per the project's memory note.

Git history for the folder shows five commits, in order: the initial site + admin + Railway config, the first analytics pass, country + date-range filtering, README documentation of that, and the calendar-picker replacement — matching the transcript narrative exactly.
